# 07 · 踩坑记录

按**犯错的代价**排序，不是按时间。每条都能复现，每条都是真踩过的。

---

## 1. Response body 一旦读取就 locked，客户端拿到空壳

**现象**：某些分支下页面白屏 / 资源 0 字节，但状态码是 200，服务端日志也不报错。

**原因**：先 `await response.text()` 读了 body，之后某个分支决定「不处理、原样返回」，
于是把这个已经 locked 的 response 直接返回 —— body 读不出来，客户端收到空壳。

```js
// ❌ 读过之后这个 response 已经不能再读第二次
const text = await upstream.text();
if (跳过处理) return response;

// ✅ 按原文重建
return new Response(text, { status: response.status, headers: response.headers });
```

**修**：订阅处理链路抽了 `passthrough(resp, original, status)`，所有「读过才决定放弃」的分支
统一走它重建。

**教训**：响应体是一次性资源。任何「先读再判断」的写法，都要保证每个出口要么消费读到的数据，
要么用它重建。

## 2. `atob` / `btoa` 只认 Latin-1，毁掉整份订阅

**现象**：`"vmess节点"` 变成 `"vmessèç¹"`；`btoa` 遇到中文直接抛 `InvalidCharacterError`。

**代价**：**最高**。这不是显示问题，它会让整份订阅内容损坏、客户端全部连不上。

**修**：抽 `b64DecodeUtf8` / `b64EncodeUtf8`，所有涉及订阅 / vmess JSON 的路径都走它。

**教训**：涉及二进制 <-> 文本的转换，先问一句「字符集是什么」。

---

## 3. VLESS 的 UUID 是 16 字节二进制，不是 36 字符串

**现象**：WebSocket 握手 101 成功，但之后服务端完全不回包。

**原因**：把 36 字符的 UUID 字符串直接塞进 header，整个协议头错位，服务端解析失败后静默断开。

```python
# ❌
uid = uuid.encode()
# ✅
uid = uuid_.UUID(uuid).bytes   # 16 字节
```

**教训**：「握手成功但数据不转发」这个症状太容易被解读成节点坏了。协议层的错位不会报错，
它只是沉默。

---

## 4. L4 判据写在 try 里，异常时被吞掉，健康节点全被判死

**现象**：79 个节点全部显示「WS ok，但 VLESS 转发无回包」，看起来像节点全坏。

**原因**：服务端回完数据会发 WS close 帧然后收尾。脚本拿到完整响应后**继续傻等到填满 3000 字节**，
第二次 `recv` 超时抛异常，而判定 `if "HTTP/" in buf` 写在 `try` 内部 —— 被 `except: continue`
直接跳过，**已经收到的有效数据随之丢弃**。

**修**：判定移到异常之外；收到响应头就跳出，不傻等；把「超时」当作「收完了」而不是「失败了」。

**代价**：给出了完全错误的结论（「你的代理节点几乎全不可用」），差点引导删掉健康的优选池。

## 5. `b"101" not in <str>` —— 字节串与字符串混用

**现象**：同上，所有节点 L3 再也上不去。

**原因**：Python 里 `bytes not in str` 直接抛 `TypeError`，而调用方是 `except Exception: continue`。

```python
# ❌ TypeError
if b"101" not in buf.split(b"\r\n", 1)[0].decode("utf-8"):
# ✅
head = buf.split(b"\r\n", 1)[0].decode("utf-8", "replace")
if "101" not in head:
```

**教训**：宽泛的 `except` 会把 bug 变成「看起来正常的失败」。宁可让异常炸出来。

---

## 6. 同一条 WS 连接上重试第二个目标，会连累全部目标

**原因**：WS 握手一次只能携带一次 VLESS 首包。在同一连接上重试第二个目标时，
服务端已经把它当作上一个流在收 —— 第一个失败时后面全部跟着失败。

**修**：每个探测目标 **新开一条连接**。

---

## 7. 用 Cloudflare 托管的站点当探测目标，会把健康节点判成坏的

**现象**：选了 CF 托管的域名做转发判据，节点全部「失败」。

**原因**：CF 对自己边缘 IP 发来的明文 HTTP 请求会直接回 400。这是目标侧行为，不是节点问题。

**修**：改用非 CF 托管的站点（`httpbin.org` / `www.baidu.com` / `www.qq.com`）。

**教训**：做端到端判据时，先确认判据本身一侧中立方。

## 8. 跨模块改函数签名，没顺调用链检查 → 全站 502

**现象**：`ReferenceError: env is not defined`，每个代理页面 502。

**原因**：`proxyRequest` 加了 `env` 参数，中间层 `dispatchProxy` 没跟着传。
而所有单元测试**全绿**（它们都没走完整链路）。

**修**：改调用链 + 新增 `tools/check-smoke.mjs`，从 `handleRequest` 进入做集成测试。

## 9. 两份缓存共用 key，产物互相串

**现象**：Turbo 的局部更新拿到一整份 docWrite 包裹的文档。

**原因**：`cachedHtmlRewrite` 与 `cachedDocWritePage` 用了完全相同的 key，
而两条分支的产物完全不同。

**修**：key 加命名空间 `rw|` / `dw|`。

## 10. path 的 `%2F` 不能 URL 解码，也不能不解码 —— 要按场景

这是本项目**唯一一次被自己的注释误导**：

- 注释写着「path 必须原样发出，百分号解码会让服务端匹配不上」
- 照做后发 `GET %2F` → **400 Bad Request**
- 改回 `parse_qsl`（会解码）发 `GET /` → 握手正常

真相是：订阅里写作 `path=%2F`，而 HTTP 请求行必须是 `GET /`。**注释是错的，断言要先验。**

**教训**：代码注释里的断言也是需要检验的。特别是当注释里出现「必须」「绝不能」时。

## 11. GeoIP 对 CDN 任播 IP 给不出/给不准国家

**现象**：67 个 IP 里只有 33 个有标注（49% 覆盖），主力 CF 优选节点全都没名字。

**真相**：三个数据源给出三个答案（主源查不到 / ip-api 说加拿大 / ipwho.is 说美国）。
任播 IP 本来就没有单一地理归属。

**取舍**：不编国名。查到就显示真实国家，查不到但命中 CF 官方段就标 `Cloudflare 任播`。
详见 [01-需求与迭代](./01-需求与迭代.md) 迭代 4。

**教训**：当一个「数据源问题」看起来可以靠加数据源解决时，先确认是不是**前提本身不成立**。

## 12. `pkill -f local-dev.mjs` 把自己的 shell 也杀了

**现象**：命令返回 `Signal: SIGTERM`，后续命令全部没执行。

**原因**：`pkill -f` 匹配的是完整命令行，而当前 bash 的命令行里就包含这个字符串 —— 自杀。
用方括号技巧（`local[-]dev`）也不够，因为同一条命令后面还要启动它。

**修**：按监听端口找 PID 再 kill：

```bash
ss -ltnp | grep ':8787' | grep -oE 'pid=[0-9]+' | cut -d= -f2 | xargs -r kill
```

**教训**：起后台测试服务时，kill 和 start 要分两条命令执行。

## 13. 本报告自身的坑：并行写代码时的字符污染

写这批文档的过程中，`架构设计 / 开发规范 / 测试体系 / 部署上线 / 运维`几份都出现过
输入法残留导致标题或列表里混入外来字符的情况，全部靠写完立刻回读才发现。

**教训**：生成大段文本后必须**回读校验**。最容易被污染的是标题和列表的首行 —— 那里既显眼
又不会被拼写检查覆盖，一旦入库就很难再被搜出来。

## 14. 配置有两个入口：面板上改了，线上跑的却是环境变量

**现象**：面板里把「只保留边缘网络内的候选」关了，保存提示成功，订阅里的候选数量没变。
翻代码才发现这个开关**面板上根本没有** —— 它只认 `env.SUB_STRICT`，而面板里那个
「同名开关」是另一个模块的、控制的是别的东西。

**根因**：同一个业务设定被拆成了两套入口 —— 一部分参数进了面板 SPEC（KV 可改），
另一部分只认环境变量。两套都是「对」的，所以：

- 不报错：面板保存成功，接口返回 200；
- 不冲突：环境变量与 KV 是两条互不相干的取值路径；
- 单测全绿：每个模块自己测自己都对；
- **但运营者永远改不到，而且看不到** —— 只能翻 `wrangler.toml` 猜线上在跑哪个值。

而且这类参数改了**要重新部署才生效**，这跟「面板保存即生效」的直觉正好相反，
排查时极易往错误方向找（先怀疑缓存、再怀疑没保存）。

**修**：面向运营的参数一律收进 `src/settings.js` 的 `SETTINGS_SPEC`，一处声明：
面板表单从它渲染、运行时从它取默认值、手册从它生成。留一条静态规则
（`check-single-source.mjs`）堵住回退 —— 除 `settings.js` 自己以外，
**任何模块直读 `env.XXX` 直接变红**；再补 `check-settings.mjs` 端到端真跑
「渲染 → 保存 → 立即生效」。

**教训**：判据不是「代码里有没有写死的常量」，而是**同一个设定有没有两份定义**。
两份定义不会报错，只会让「改了没反应」变成一个查不出原因的谜。

## 15. 面板改了节点配置，订阅毫无变化：引擎每次请求都覆盖自己的配置文档

**现象**：在面板改「节点 ID / 节点地址 / 节点路径」，保存提示成功；清空浏览器缓存、
换客户端、重开订阅，输出里的节点还是老样子。

**根因**：这几个字段的存储是**代理引擎自己的配置文档**（KV 里的 `config.json`）。
面板写入的确实是它，一点没写错 —— 但 `vendor/vless.js` 每次请求都会用**环境变量与
请求上下文**再覆盖一遍自己这份文档：

```js
userID = (envUUID && uuidRegex.test(envUUID)) ? envUUID.toLowerCase() : 由口令派生
```

于是面板值与运行时值成了两条路：面板改的是「文档」，引擎认的是「环境变量」。
两条路都自洽，所以面板保存成功、接口 200、配置确实落了库 —— 只是没人读。

还有两个由此衍生、更难发现的变体：

- 填了一个「看起来像 UUID 但不是 v4 形态」的值 → `uuidRegex` 不匹配 → 引擎**默默**
  改用派生 UUID。面板说保存成功，实际节点 ID 完全没变。所以格式判断必须与引擎的
  正则逐字一致，并且要在**写入前**拦住（见 `util.js` 的 `isUuid` + 注册表的 `validate`）。
- 把节点地址清空 → 面板写入空数组 `[]`，而引擎的兜底是 `if (!config_JSON.HOSTS)`，
  空数组是**真值** → 兜底不触发 → 节点地址变成空。清空必须**删掉这个键**，不能写 `[]`。

**修**：把有效值回灌成引擎认的环境变量（`settings.js` 的 `engineEnvFor`），
让「面板 → 存储 → 引擎」成为一条链；注册表里这类字段标 `store: 'engine'`，
读改写整份文档以保留引擎的其它键；清空走 `writeEngineField`（空数组 → 删键）。

**教训**：保存成功 ≠ 生效。「存储里有没有值」和「运行时读的是不是它」是两个问题，
面板只验证了前者。

## 16. 面板改了标注样式，订阅输出没变：取值分了两份

**现象**：面板上把节点备注的国家标注从「中文代码」改成「旗帜」，保存成功，订阅里的备注没变。

**根因**：「标注开关 + 样式」这两个值被解析了两遍：

- 面板写入的那条路写进 KV；
- 订阅输出那条路（`nodetag.js`）**只读环境变量**，压根没看 KV。

两处都能跑、都不报错，只是读到的东西不同。修的时候还顺带发现第三个名字：
旧实现把数据源标注成 `'kv'`，而面板只认 `panel / env / default / legacy` ——
连「这个值从哪来」都各说各话。

**修**：取值只留 `readSettings` 一条路，归因只留 `settingsSource` 一处；
`styleFrom` 变 async（要 await 注册表），调用链全部跟着 await。
`check-nodetag.mjs` 里补了「没有面板值时回落到环境变量种子」和「清掉面板值后回到环境变量」
两条回归，把三级取值钉住。

**教训**：同一个设定的**读取入口**也必须只有一个。「写在哪里」统一了还不够 ——
读取侧只要还留着一份自己解析的实现，就会继续对不上。

## 17. 「保存成功」而值没变：写入侧把不认识的字段静默忽略

**现象**：接口调通、返回 200、提示「已保存」，但配置项的值一个都没变。

**根因**：`saveSettings` 只遍历 `SETTINGS_SPEC` 里的字段（`if (!(key in patch)) continue`），
**认不出来的键直接跳过**。于是只要字段名对不上——写错一个字母、或者某个调用方还在用旧别名
`{enabled, style}` 而注册表里叫 `node_tag_enabled` / `node_tag_style`——结果就是：
不报错、不抛异常、日志干净、返回体还是「已保存」。

这是第 14 条的续集：**入口**统一了，**写入侧**还留着一个静默的漏斗。

**修**：不认识的键直接 400 并点名是哪个字段：

```
未知配置项：enabled、style（字段名以 settings.js 的 SETTINGS_SPEC 为唯一真源）
```

顺带把一条原本写成 `400 或者 200 但没写进库都算过` 的断言收紧成硬要求 ——
那种「两种都算过」的断言等于没查，恰恰放过了这个 bug。

**教训**：凡是「静默忽略」的分支都要问一句「忽略之后，调用方能不能知道」。
不能让调用方知道，就等于把错误藏进了「一切正常」里。

## 18. 同一个配置长在所有选项卡里：表单是手写的，不是从目录渲染的

**现象**：「优选池 / 健康检查」的卡片在每个选项卡下都出现；「订阅链接」和「节点国家标注」
两张卡片，字段、控件、帮助文字跟别处都不一样 —— 因为它们是在页面模板里**手写**的。

**根因**：接口目录（`api-catalog.js`）只驱动了「配置页」的渲染，归属功能选项卡的那部分
不在配置页出现，于是这些页面的卡片只能各写各的 HTML 与保存脚本。
手写一份的代价：新增一个动作要在页面里再加一段 `onclick`；改一个字段要在两处同步；
某个选项卡忘了套统一的容器类，它的输入框就比别处窄一圈。

**修**：给字段加 `panel: '<目录项 id>'` 投影标记（一个字段只能投到一张表单），
页面模板里只写 `settingFormById('node-config')`；选项卡自己的动作按钮改由
`toolItemsForTab('<tab id>')` 从目录渲染，目录项用 `body` 声明固定请求体。
`check-configui.mjs` 第 4 段钉住「同一份配置全页只有一张可编辑表单」。

**教训**：只要界面上还有手写的第二份，它迟早会和真源分叉。判断标准不是「有没有界面」，
而是**界面是不是从真源渲染出来的**。

## 19. 开了部署压缩后，面板一直「加载中」、按钮全失灵：注入脚本靠全局名传数据

**现象**：给 `wrangler.toml` 加上 `minify = true` 压掉 38% 体积，部署成功、首页正常，
但一进「CF 用量」「访问统计」两个面板就卡在加载态，按钮点了没反应。刷新、换浏览器都一样。
Worker 侧的日志**一条错误都没有**。

**根因**：这两个模块的前端脚本是「写成本地函数、再用 `toString()` 注入浏览器」的，
数据靠这样一段带过去：

```js
`${KEEP_NAMES_SHIM}var CF_TREND_METRICS=${CF_TREND_METRICS_JSON};(${cfInit.toString()})();`
```

前半段的 `CF_TREND_METRICS` 是**硬编码的字符串字面量**，后半段函数体里引用的
`CF_TREND_METRICS` 是**模块级标识符**。不压缩时两者同名，一切正常；开了 minify 之后
模块级标识符被重命名成一个字母，字面量还是 `var CF_TREND_METRICS=` —— 名字对不上，
注入到浏览器的脚本**第一行就 ReferenceError**，整段中断。

之所以查不出来：错误发生在**浏览器**里，Worker 侧完全无感；而本地 20 套自检跑的是
**源码**（不压缩），源码层面这两个名字当然是同一个，所以全绿。

**修法**：数据改成**实参**传入，不依赖全局名：

```js
`${KEEP_NAMES_SHIM}(${cfInit.toString()})(${CF_TREND_METRICS_JSON}, ${CF_STATUS_KLASS_JSON});`
```

函数体和调用处属于同一次压缩产出，命名必然同步，天然免疫重命名。

**后续（同一天）**：改完实参传参又部署了一次，线上仍然「所有页面 JS 加载异常」。这回的
受害者换成 70 KB 外壳脚本里**引用了模块级标识符的函数** —— 压缩把那些标识符改名成单字母，
浏览器侧直接 `ReferenceError: o is not defined`。结论没变：只要还有代码把「源码里的名字」
当成跨边界的契约，压缩就迟早在某个地方炸，而且炸在浏览器里、Worker 日志一条不剩。

**决定：回滚压缩，不再启用**（`wrangler.toml` 里留了说明，避免以后有人手痒再开一次）。
867 KB 距免费版 1 MiB 上限还有余量，体积不是当前瓶颈；为省 38% 换一次线上全站不可用，
这笔账不划算。**实参传数据这条纪律保留** —— 它本身就更健壮，开不开压缩都该这么写。

**教训**：**产物形态变了，源码层面的自洽就不作数了。** 凡是把源码当字符串送出去的地方
（`toString()` 注入、模板拼接、代码生成），都要假设标识符会被改名，只能依赖
**同一份产出的内部结构**，不能依赖名字本身。另外——本地自检跑的是源码，压缩产物的
问题它一条都抓不到，这类改动必须有专门针对产物的检查。

## 20. 部署脚本日志全绿，wrangler 却说配置不合法：子进程读的是磁盘，不是你的变量

**现象**：把 `wrangler.toml` 里的资源 ID 改成占位符、由 `prepare-deploy.py` 在部署前渲染
（见 [01-需求与迭代 · 迭代 16](./01-需求与迭代.md)）。第一次推送后 CI 红了，Deploy 步骤
停在 `Prepare config`：

```
✘ [ERROR] Processing wrangler.toml configuration:
  - Expected "name" to be of type string … but got "__WORKER_NAME__".
```

而脚本自己打出来的三行日志全是绿的（"已移除 KV 绑定"、"R2 降级"、"渲染完成"），
看起来像是 wrangler 撞了鬼。

**根因**：脚本是这个顺序 ——

```python
text = render(text, values)                 # 先在内存里渲染
if backend == 'd1':
    subprocess.run(['npx','wrangler','d1','migrations','apply',...])   # 迁移（另一个进程）
with open(path, 'w') as fh: fh.write(text)  # 最后才写盘
```

迁移是**另一个进程**去读磁盘上的 `wrangler.toml`，它读到的是还没落盘的占位符版本。
脚本自己的变量是对的、最后写出的文件也是对的，唯独中间那一步读的是旧的。

**为什么看着像 wrangler 先跑**：Python 的 stdout 在非 tty 下是块缓冲，脚本的 print
要等进程退出才刷出来；wrangler 的 stderr 是无缓冲的。于是日志里 wrangler 的报错
**排在脚本日志之前**，顺序本身就把人往反方向带。

**修法**：渲染完立刻写盘，再跑迁移。同时补了一条自检 —— 用一个假 `npx` 把「迁移那一刻
磁盘上的文件」抄下来，直接验那份内容（光断言"最后写出来的文件对了"抓不到它，因为
那个文件最后确实是对的）。另外再用源码行号把「写盘必须排在迁移之前」钉住，避免哪天
被无意调换。

**同一轮还踩到两个**：

- CF 的 R2 列表接口返回 `{"result":{"buckets":[...]}}`，而 D1 / KV 返回 `{"result":[...]}`。
  照搬同一个 `cfList()` 会遍历到 dict 的**键名**（`'str' object has no attribute 'get'`），
  于是"桶明明在"被判成不存在、转头去新建。
- CF v4 接口**失败时也可能回 200**（`success: false` + `errors`）。只看 `result` 会把
  "权限不够"读成"一个资源都没有"，然后脚本兴冲冲去新建，撞上重名错误。

**教训**：**脚本里凡是「交给另一个进程去读的文件」，必须先落盘再调用**；而且这类事故的
判据不能只验最终结果 —— 要验**那个进程当时看到的输入**。另外，缓冲造成的日志乱序
会主动误导排查，看到"报错在日志最前面"别急着相信时间顺序。

## 21. 判据自己也有 bug：固定字符窗口会越过 `);` 读到下一句

给「候选接口每个出口都要回带测速口径」写判据时，用的是：

```js
const withLimits = rets.filter((i) => /limits/.test(block.slice(i, i + 300)));
```

牙齿验证（故意把拉订阅失败那个出口的 `limits` 删掉）**居然还是绿的**。原因是两个 `return`
之间只隔了约 200 字符，300 的窗口越过了 `);` 与 `}`，直接读到下一个 return 里的 `limits`，
于是"这个出口没带"被判成"带了"。

改成按**语句边界**取，而不是按字符数：

```js
const withLimits = rets.filter((i) => /^[^;]{0,400}limits/.test(block.slice(i)));
```

`[^;]` 天然停在本条语句的分号上，不会滑到下一句。

**教训**：**静态判据里的"窗口"必须是语义边界，不能是字符数** —— 字符数看着够短，
实际跨过一条语句只需要一个 `);`。这类 bug 只有牙齿验证能抓出来：改坏实现却发现检查不红，
说明红的是实现、绿的是判据。

**延伸**：这一条与第 10 条同源（"做判据前先确认判据本身是中立可靠的"）——
判据不可信时，全绿的报告比红灯更危险。

## 22. 判据的**终点**也不能靠猜：切到空串时两条检查一起变红，却不说是为什么

给订阅出口写静态判据时，取了这么一段：

```js
const block = routerSrc.slice(routerSrc.indexOf("path === '/sub'"), routerSrc.indexOf('stranger'));
```

而 `stranger` 那段（`if (stranger) { ... }`）恰好排在订阅分支**前面** ——
`indexOf('stranger') = 4625 < 6470`。`slice(6470, 4625)` 得到**空串**，
于是 `clone()` 与 `Promise.race` 两条判据同时失败。

因为一来代码是新写的、还没跑通，我第一反应是「判据定位错了=我没写完整实现」，
于是去改实现；又因为列表里写的是 `check('...')` 结果红，看不出 block 长度，
排查绕了一圈才发现：**两只眼看的就是空串**。

**修法**：先把「边界找对了」本身做成一条断言：

```js
const start = routerSrc.indexOf("path === '/sub'");
const end = routerSrc.indexOf("path === '/edt'", start);   // 起点**之后**的下一段路由
check('订阅分支的切片边界找对了（判据本身要验）', start > -1 && end > start, `start=${start} end=${end}`);
const block = routerSrc.slice(start, end);
```

并把 `block.length` 塞进失败详情 —— 下次再见它红，一眼就知道是 `长度 0`。

**教训**：第 21 条说的是「窗口用字符数会越过 `);`」；这一条是它的镜像 ——
**终点用「猜一个关键词」同样危险，而且更隐蔽**：猜错时机不会报错，只会静默退化成空串。
凡是 `.slice(a, b)`，都要断言 `b > a`。

## 24. 缓存类检查是「假绿」重灾区：不先把旧值塞进缓存，验的其实是「缓存天生是空的」

给 `sites.js` 加进程内缓存之后，顺手给 `check-smoke.mjs` 补了第 [10] 段，验「站点增删改之后立刻生效」。
九条断言全绿，看着很稳。做牙齿验证时把 `admin.js` DELETE 分支的 `invalidateSite(id)` 删掉 ——
九条里**只有一条红**，「删除后列表里也没有了」照样绿。

查下去发现它是**碰巧绿的**：前面「改 slug」那一步也调了 `invalidateSite()`，
顺手把 `listCache` 清了；于是轮到删除时列表缓存本来就是空的，
下一次读必然 miss、必然拿到真实数据 —— 清没清都一样。

```
cache 是 cold 的时候：  写 -> 不清缓存 -> 下次读 miss -> 读真值 -> ✅（假绿）
cache 是 warm 的时候：  写 -> 不清缓存 -> 下次读 hit  -> 读旧值 -> ❌（这才验到了）
```

同样的问题也藏在「新增后列表里立刻就有」上：那段之前没有任何列表读操作，
`listCache` 初始就是 `null`，根本无从谈起「有没有被失效」。

**修法**：每一次写操作**之前**先做一次对应的读，把一份「写着没有 / 写着旧值」的副
本先装进缓存：

```js
const absent = await open(slug);        // 先把新后缀的「不存在」写进负缓存
ok('前置：新后缀此刻不存在（负缓存里已有一份「没有」）', absent === 404, `HTTP ${absent}`);
```

前置自己也是一条断言 —— 万一步骤本身没把缓存填上（比如路径改了、返回不再是 404），
它会先红，不会让后面几条继续假装通过。

**教训**：**验缓存必须在 warm cache 上验。cold cache 下的全绿说明不了任何事** ——
它验的是「缓存里原本没东西」，不是「写入之后有没有清」。
凡是「写完立刻也要看到新值」的断言，写之前都得先把旧状态装进去。

## 25. 防御散落多处会互相掩护：三份清理里砍掉一份，检查照样全绿

接着做第二组牙齿验证：删掉「改 slug」路径上
`invalidateSite(ns)` 那份 —— 不红；换砍末尾 `invalidateSite(keyId)` 那份 —— 也不红。

原因是这条路径上有三处能清到新 slug：

```
改名分支里  invalidateSite(ns)        ← 新 slug
改名分支里  invalidateSite(id)        ← 旧 slug
PUT 末尾    invalidateSite(keyId)     ← keyId 在改名后 === ns，等于又清一遍新 slug
```

新 slug 被两份覆盖，**三选二就够了**，于是砍任何一份都不影响结果。
看起来是双保险，实际是：每一份都不足以自称是那条保证 —— 被后人当成冗余删掉时，也不会有任何信号。

**修法**：把散落的清理收拢到一处 —— 写完 KV 之后统一作废，
并用 `renamedFrom` 这种显式变量替下「同一个地方清两次」的写法：

```js
await runtime.KV.put(kvKey(keyId), JSON.stringify(site));
invalidateSite(keyId);
if (renamedFrom) invalidateSite(renamedFrom);   // 旧 slug 只在这里有机会被摘掉
```

收拢之后重做牙齿验证，四份清理**缺哪一份坏哪一份就会有对应的检查变红**，互不遮掩
（具体到哪条红已写进 `check-smoke.mjs` 第 [10] 段的注释里）。

**教训**：**三份互相掩护的防御，不如一份被检查盯住的防御。**
多处重复做同一件事时，每一份都不是必要的 —— 而「不必要」意味着删掉它没有任何信号，
也就意味着它随时可能被当成冗余删掉。要就收拢到一处，并对那一处做牙齿验证。

## 26. 牙齿验证不能只数失败项：脚本崩了，也会被误报成「这段检查没有牙齿」

给存储降级做完检查，照纪律做牙齿验证：把 `memstore.js` 故意改坏 10 处，每处都应让它变红。
第一次跑出来有 3 处报告「改坏了却是绿的 —— 这段检查没有牙齿」：

- 降级后仍去读后端
- 每次绑定都新建状态
- 面板阈值同步不进来

直觉反应是「这三段写得不够狠」。但把它们单独跑一遍，输出是这样的：

```
Error: D1 配额超限
    at Object.get (tools/check-storage.mjs:42:68)
    at Object.get (src/memstore.js:318:31)
```

**脚本是崩的** —— 实现坏掉以后，断言里的 `await p.get(key)` 抛了未捕获异常，
进程当场结束，连汇总行都没打印。而对照脚本是这样判定的：

```js
const m = out.match(/失败 (\d+) 项/);
const n = m ? +m[1] : -1;
if (n > 0) console.log('抓住'); else console.log('没有牙齿');   // 崩了 => -1 => 走到「没有牙齿」
```

崩溃被归类成了「没有失败项」，于是显示成绿的。**我差点据此去给已经够狠的检查加料。**

这件事有两个层面。表层是对照脚本的判定写漏了 —— 退出码非 0 必须先于「数失败项」判断：

```js
if (r.exitCode !== 0 && reds.length) 通过;
else if (r.exitCode !== 0) 不通过（崩了但读不出是哪一项）;
else 不通过（改坏了却是绿的）;
```

深层的问题是：**崩溃虽然会让 CI 变红，却是最没用的那种红。** 一屏调用栈不告诉你哪一条约定
被违反了。夜里排障时这和没有提示差不多。所以这一步真正的修法是两头一起改：

1. 断言里的读一律换成会吞异常的助手，坏实现拿到的是一个可读的哨兵值而不是异常：

   ```js
   const THREW = '<读的时候抛异常了>';
   async function read(p, k) { try { return await p.get(k); } catch { return THREW; } }
   ```

2. 判定口径收紧成「**不仅要红，还要红得看得懂**」—— 打印出失败项才算通过。

改完重跑，同一批变异从「崩溃」变成干净地红 1~15 项，每条都点名到具体断言。
这套对照脚本同样没有留在临时目录里，而是固化成 `tools/tooth-storage.mjs`
（14 个变异 + 上述判定口径，跑一条命令即可复验，已挂进 CI）。

**教训**：**写「这段代码应该变红」的对照脚本时，退出码与失败项要分别判定 —— 崩了是非 0，
但它不代表检查生效了。** 更进一步：好的检查崩了和红了是两件事，前者只能拦住，后者才能定位；
让坏实现在断言里得到一个可读的值，比让它抛异常更有用。

**顺带的教训**：第一版的替换脚本用了正则把 `await p.get(` 全量换成 `await read(p, `，
把 `read` 自己的函数体也换掉了，于是自递归、所有断言一起拿到哨兵值 —— 一次性 14 项变红。
**写机械替换时先跑一遍再读结果，不要相信「替换了 N 处」这一句输出** —— 处数对了不代表每一处都对。

## 27. 带着真实数据跑一遍：一次撞出四条「只看代码怎么读都对」的错

这一轮子做的事是「把线上 D1 里的数据导出来，做成分片种子，让站点在不碰存储的情况下跑起来」。
代码、单元测试、端到端自检早就全绿了。等到真拿那份 2990 行的生产数据跑一遍，一口气冒出四个问题——
它们的共同点是：**只看代码，每一处都读着是对的。**

### 一、过滤前缀写错了一个字母，整类键静默漏过去

`DEFAULT_SKIP` 里写的是 `stats:`。而库里实际的统计键是**单数**的 `stat:`（`stat:sub:2026-09-18`）。
`startsWith` 两条都对不上，于是几百 KB 的流水被当成配置一起导出。

这类错误不会报错：种子照样生成、照样能解析、站点照样起来，只是里面混着一堆没用的东西。
盯住它的是一条盯着真实形态的断言，外加一个只删 `'stat:'` 这一个词表项的变异。

```js
export const DEFAULT_SKIP = ['stats:', 'stat:', 'st:', 'visit:', 'latency:', 'geoip:', 'log.json'];
//                                     ^^^^^^ 库里是单数形态；为什么会有两个，注释就写在它上面
```

### 二、远程接口的行是数组还是对象，猜错了就直接崩

D1 的 `/raw` 端点返回的行是 `[["键","值"]]` 这种**数组**，而代码里写的是 `row.key` / `row.value`。
它是「导出工具」里唯一不会被离线自检碰到的一段，所以一直没红过——第一次真连线上就 `map is not a function`。

修法不是改成 `row[0]` 就完事：`/query` 与某些 SDK 返回的是对象形态，两种都得认。
于是把它单独抽成一个纯函数 `cfRowsToEntries()`，**按 columns 定位**（列顺序不固定也不会取错），
再补上四种形态的断言和一个「故意按对象取」的变异。

> 教训写进 `AGENTS.md` 第 7 节：凡是涉及外部数据的环节，至少拿一份真实样本跑一次。

### 三、目标站自己返回 404，于是「种子完全正常」被判成失败

站点 `uhdnow` 的目标 `v1.uhdnow.com` 自己就返回 nginx 的 404。
而那条断言写的是「不是 500/404 就算通过」——于是「种子读到了、代理也通了」被判成失败。

翻案的两次尝试都站不住：
先用「本站渲染的『站点不存在』友好错误页」当标记，结果发现项目有**前缀丢失自愈**，
任何未知路径都会被拼到第一个站点上再代理一遍，那张错误页通常根本不会出现——判据等于空验。

最后用的判据是直接得多的那一版：**同一条请求，灌种子前后各打一次，两边必须不一样**。
它不依赖目标站返回什么，也不依赖项目自己的兜底规则；只要种子没生效，两次就一模一样。

### 四、用例里的站点少给了字段，那条断言一直在验一个空响应

顺着上面那条查下去才发现：`check-storage` 里那个「演示站」只给了 `target`，缺 `scheme` / `host`，
代理引擎拼不出目标地址，直接返回了空 **204**。而断言看的是「不是 500/404」，204 当然通过。

也就是说，**这条检查跑了那么多轮，从来没真的碰到过站点**。
补齐字段之后，同一条断言立刻从「204 / 204」变成「有种子 HTTP 200，没种子 HTTP 204」。

### 沉淀：状态码不能单独当判据

被验系统下游那个目标站，返回什么都可能是合理业务行为。
要验「有没有用到我给的这份数据」，就得用**相对判据**——
灌数据前后打同一条请求，要求两者不同。它比任何阈值都难造假。

顺带记住：换判据的时候，**旧判据为什么失效**要写进注释。
不写的话，下一个人会把它改回去——因为它看起来明明更简单。

## 28. 后端全绿不代表页面能用：注入脚本的一处转义让 97 个按钮全部失灵

**现象**：内存模式上线后，用户反馈「页面所有功能都不能用」。
查下来是这样一组看起来互相矛盾的事实：

| 查的地方 | 结果 |
|---|---|
| 28 个 GET 类接口 | 全部 200 |
| 写 → 读回 30 轮 | 全部一致 |
| 面板 HTML | 200，196 KB，97 个按钮、21 个分区都在 |
| Worker 日志 | 一条报错都没有 |
| 浏览器控制台 | `Invalid or unexpected token` |
| 浏览器侧实际状态 | `window.api` / `switchPane` 全 `undefined`，**97 个按钮绑了 0 个事件** |

**原因**：运行模式状态条里，写回结果的那句提示是这么写的：

```js
alert('写回 ' + n + ' 个'
  + '\n跳过（存储里已被改过）' + m + ' 个');
```

问题不在 `\n` 本身，而在**这段代码是被模板字符串拼进 HTML 的**。
JS 解析那个模板字符串时就把 `\n` 解释成了真实换行，等它到达浏览器，
已经是「单引号字符串里出现裸换行」——直接 SyntaxError，整个 script 块一行都不执行。
同一个文件里 2050 / 2093 行用的是 `'\\n'`（正确写法），这次新写状态条时跟着错的那版走了。

**为什么难查**：这条链路在**服务端是零症状**的。
页面渲染得出来（HTML 在服务端就生成好了），接口全绿，日志干净，
唯一的报错写在用户的浏览器控制台里——而那是服务端测试永远碰不到的地方。
只看状态码的排查方式，在这类问题上完全失效。

**修法与防复发**：

1. 模板字符串里的转义序列一律写双反斜杠，`'\\n'` 而不是 `'\n'`。
2. `tools/check-smoke.mjs` 新增第 [11] 段：**把页面里每段 script 原样抽出来过一遍语法**。
   从此再写错是自检红，而不是用户在页面上发现。
3. 同一坑的另一种发作：注释里也不要出现反引号。
   我会犯第二次——修这个 bug 时写的注释里用了反引号，
   结果它提前结束了外层模板字符串，`<script>` 三个字被当表达式求值，报 `script is not defined`。

### 顺带：`git add -A` 会把本地工具的产物一起提交

这次排查中途用 `prepare-deploy.py --local` 起了本地 worker，
它会把 `wrangler.toml` 里的占位符**渲染成真值**。之后 `git add -A` 提交临时诊断脚本时，
这份被渲染过的配置一并进了版本库，CI 里 `check-wrangler` 直接红 9 项
（占位符数量对得上 → 0 个）。

本地工具会改文件的，提交前先看一眼 `git status`。
这次诊断脚本稳妥的做法是单独 add，别图省事用 `-A`。

> 沉淀进 `AGENTS.md`：新写的断言必须证明它会红；服务端检查照顾不到浏览器侧，
> 页面类改动要有「浏览器视角」的证据。

## 29. 配额打满 = 发不了版：一次额度超限，升级成连 d1 绑定都上不去

### 现象

把 `STORAGE_BACKEND` 从 memory 改回 d1、部署，workflow 在建表这步红掉：

```
subprocess.CalledProcessError: Command '['npx', 'wrangler', 'd1', 'migrations',
'apply', 'any-proxy-db', '--remote']' returned non-zero exit status 1.
```

这次想要的只是「能不能发版」，但画面是这样的：

| 环节 | 状态 |
| --- | --- |
| wrangler 渲染配置 | 成功，d1 绑定写进了 wrangler.toml |
| d1 迁移（建表） | **失败** —— 配额打满，迁移本身也要读写额度 |
| wrangler deploy | **根本没跑到** —— workflow 在中途就 exit 1 了 |
| 线上 Worker | 还是上一版（memory 部署、没有 d1 绑定） |

### 原因

`check=True`。迁移这一步失败就让整个 workflow 退出。可迁移的作用只是**建表**，
而表在这次配额打满之前早就建好了 —— 这一遍重跑的意义是零。

代价却被放大了：Worker 既没更新，也没拿到 d1 绑定，而面板上什么都看不出来。

### 权衡：不是「放宽规则」，是把它降到应有的重量

项目里早就有先例：R2 建不出来就删掉绑定、让部署继续（Worker 侧会降级到纯 Cache API）。
d1 迁移完全同源 —— Worker 侧有更完整的一条退路：读不到存储就降级到内存模式，
用部署时注入的种子照常服务。所以让它走向同一套处理。

但「允许失败」从来不等于「悄悄失败」，这次写明三处：

1. `check=False`，失败时**不退出**；
2. 打 `::error::` annotation —— 运行详情页会标红，躲不掉；
3. 写进 `$GITHUB_STEP_SUMMARY`，里面说清「这次没建表」＋ 配额恢复后的三步收尾
   （检测存储 → 写回存储 → 切回存储模式），以及「新空库必须让它重跑一次」。

另外保留 `workflow_dispatch` 的 `skip_migrations` 输入（默认关，要勾选才生效）：
配额确定打满时，连那一次注定失败的迁移都不用等。

### 顺带：检查本身也会骗人 —— 拿源码行号判行为顺序

修完上面这些，CI 里 `check-wrangler` 红了，失败项：

```
写盘语句排在迁移之前（不是靠巧合） -> write@9757 / migrate@6157
```

这条断言是把源码里 `fh.write(text)` 与 `'migrations', 'apply'` 的
`indexOf` 位置比大小来判断「写盘先于迁移」。而我把迁移抽成了 `apply_migrations()` 函数，
函数定义自然排到了写盘之前 —— 行为完全正确，行号却「判定」成违规。

**拿源码文本位置证明运行时行为，改个代码组织方式就误报。**
改成比迁移那一刻磁盘上的内容与最终产物是否逐字节相同；顺手把假 npx 也改成**只记第一次**
（`[ ! -f dump ]`），否则谁在写盘之前提前触发过一次迁移，最后留下的是好的那份，查不出来。

### 沉淀

- 部署流程里「必须成功」的步骤要逐个过一遍：它的失败真的是致命的吗？不是就不要 `check=True`。
- 允许失败的每一处都要留响声（annotation ＋ 摘要），否则等于删掉了这条信息。
- 断言里出现 `indexOf` / 行号比较时先停一下：这是在用静态位置冒充动态行为。

> 沉淀进 `AGENTS.md`：检查不要靠源码文本位置判断行为顺序。

## 30. 订阅失败的三种伪装：病因（没身份）、症状（没节点）、表现（伪装 404）

### 现象

用户报「拉取订阅失败了」，附带 Stash 的 YAML 解析报错。同一个链接连打 8 次，
`fmt=clash` 全部 503「服务端没有取到节点清单」；不带 `fmt` 时，8 次里约 1/3 返回真正的
节点清单（25 KB），其余返回 613 字节的 nginx 欢迎页。**同一个部署、同一条链接、同一分钟，
两种结果。**

### 排障里最贵的三件事

**一、每一层都在改口供。** 真正断掉的那层什么都没说：

| 层 | 它说的话 | 实际病因在这一层的可见度 |
| --- | --- | --- |
| 结果 | `yaml: found character that cannot start any token`（客户端） | 完全看不见 —— 只知道拿到的是 HTML |
| 表现 | nginx 欢迎页 / 613B | 伪装 404，看起来像「链接不存在」 |
| 症状 | 503「没有取到节点清单」 | 指向「存储里没数据」 |
| **病因** | **冷启动的 isolate 拿不到节点 ID** | 没有任何一行提到它 |

`worker.js:149` 的全局兜底把「订阅内部出错」渲染成伪装 404 —— 伪装的目标是骗过扫描器，
代价是把自己的排障方向也一起骗了。

**二、误以为随机的其实是确定的。** 先以为是渲染层的问题（本机渲染那一层确实是新写的），
改完再测仍然一半失败。真正的开关不在代码里：**内存模式下，worker 有多少 isolate 不由我们
控制**，只有运气好在 memory 里还留着数据的那几个实例能吐出节点清单，冷启动的那批一律空仓。
「同一份部署两种结果」不是抖动，是两种情况本来就同时存在。

**三、最后靠数学锁死。** 订阅 token 的推导口径是 `MD5MD5(域名 + 节点 ID)`（引擎 `MD5MD5` 的
特别之处是取第一次摘要十六进制的 `slice(7,27)` 再摘要一次）。代进去一对，(域名, 节点 ID)
组合正好等于用户链接里的那个 token —— 到这一步才敢下结论：

```
MD5MD5("proxy.520215.xyz" + "90cd4a77-141a-43c9-991b-08263cfe9c10")
  = d662b808e0a23961eb81ce8d40647f4d     ← 正是链接里的 token
```

于是链路清楚了：节点 ID 的取值顺序是「存储里的 `config.json` → 环境变量 `UUID` → 拿管理员
密码临时派生」。前两条都够不着时，引擎安静地走到第三条 —— 派生出来的 ID 和发出链接时的
不是同一个，token 必然对不上，请求落进伪装页，一路传到渲染层只剩「一行节点都没有」。

> 顺带在这一轮里发现另一条**不报错的**同类缺陷：内存模式切换时的预捞清单漏了
> `ADD.txt`（引擎自己读的优选 IP 池）。少了它不报错，而是退回「随机 IP」—— 策展好的节点
> 连同备注全部消失，看起来只像网速变差。

### 修复（分层各修一处）

1. **失败要说到病因**（`src/router.js`）：进入引擎之前先自查身份。缺节点 ID 就直接说
   「本实例未取到节点身份……请切回存储或用环境变量 `UUID` 注入」，而不是「没有节点清单」。
   正文只说「没有」，不吐任何 ID / 域名取值 —— 这个端点陌生人也能打到。
2. **该预捞的别漏**（`src/memstore.js`）：订阅赖以生存的键集中成 `SUB_MINIMAL_KEYS`，
   其中由引擎自己读的那几个单独标成 `ENGINE_KV_KEYS` —— 改它们的只有引擎自己的 admin 路由，
   面板配置项里搜不到，最容易漏。
3. **三处对齐**（`tools/check-storage.mjs`）：常量 ↔ 预捞清单 ↔ 引擎源码，双向断言。

### 沉淀

- **配置或凭证级的前提条件要在入口处自查**，别让下游的表现去猜。出问题时差的那三小时，
  全花在「症状指向的地方没有病因」上。
- **明确写出某个值的所有取值路径**（这里就是「存储 → 环境变量 → 派生」），
  派生兜底要格外小心：它让取不到值这件事**永远不报错**。
- 服务的每一层都可能在改写失败的样子：客户端的解析器、伪装页、全局兜底、再往上是
  CDN 的错误页。怀疑哪一层，就把那一层的原始输出直接抓出来看。

> 沉淀进 `AGENTS.md`：用伪装页兜住内部异常，等于把病因也一起藏起来 ——
> 可以失败，但要说到病因在哪一层、下一步做什么。

## 31. 修好一头漏另一头：主订阅好了，临时订阅照样坏

### 现象

上一轮把 `/sub` 的 clash / sing-box 改成服务端本机渲染，主订阅修好了。
紧接着用户报「临时订阅不能用了」—— 同一个坏掉的外部转换后端，换了条路进来。

### 原因

`/tsub/<id>` 是另一条链路，它的多格式输出当时是**原样透传引擎响应**：

```js
const fmt = url.searchParams.get('fmt');
if (fmt === 'clash' || ... ) return resp;     // 引擎 → 外部转换后端
```

而引擎判定订阅类型时**看 UA**（第 376 行 `ua.includes('clash')` → `clash`）。
所以 Stash 这类客户端拉临时订阅时，链接上根本不用带 `fmt=clash` —— UA 已经把它送进
clash 分支，接着就转给那台外部后端。旧代码里那个 `fmt` 判断只在用户**显式**带参数时才
成立，等于「自动识别的那一路从来没被本机渲染覆盖过」。

两个入口各自写了一遍「要不要渲染」的判定，于是修一处漏一处是必然的，不是运气差。

### 修复

把判定抽成一个函数 `subOutputKind(url, request)`，`/sub` 与 `/tsub` **共用一份**，
两边都不再自己判 UA。顺手一并改掉：

- 临时订阅整条链没有异常兜底：`tempSubToken()` 要动 MD5，失败就一路抛到
  `worker.js` 的全局兜底 → 伪装 404（和第 30 条是同一个坑）。现在令牌改成惰性传入
  `tokenOf`，连同「算令牌」一起落在 `nativeSubResponse` 的兜底里。
- `new Request(url, request)` 拿不拿得到 `cf` 取决于运行时实现，而引擎一上来就要读
  `request.cf.colo`。宁可显式带上，也别赌。
- 记录读不到 / 已过期 / 被停用三种情况，响应仍是光秃秃的 404（不向探测者解释），
  但**病因进日志** —— 内存模式下冷启动实例全都读不到记录，不响就只能靠猜。

### 沉淀

- **同一类判定只写一份**。存在两个入口时，「修好一头」从来不等于「修好了」。
  改完一处，先问一句：**另一头走的是同一个函数吗？**
- 判断「要不要自己渲染」这类分支时，注意引擎/上游还会**按 UA 自己再判一次**：
  上游的隐式分支不会出现在你的参数判断里，却决定了实际走哪条路。
- 给「两边同路」写断言时，判据要能真的区分两条路（这里靠「异常被谁兜住」来区分，
  因为本机环境下引擎必然因 MD5 抛错）。静态地搜源码里有没有那行调用不算数。

> 沉淀进 `AGENTS.md`：改一处之前先找同类的其它入口；共用判定是唯一能防止
> 「修好一头漏另一头」的手段。

## 32. 不要用猜测代替取数：D1 配额到底是怎么爆的，猜了三轮都猜错

### 现象

站点连续两天自动降级到内存模式、两条订阅同时失效。想查清是哪类操作把 D1 打满的，
本机却什么都查不了：

```console
$ curl https://api.cloudflare.com/client/v4/user/tokens/verify
curl: (7) Failed to connect ...        # http=000
$ getent hosts api.cloudflare.com
198.18.0.5     api.cloudflare.com      # 沙箱把 DNS 劫持到假网关
```

`github.com` 同样被劫持到 `198.18.0.14`。仓库 remote 配的 `gh-proxy.com` 能代理 git
与 GitHub API，但明确不代理其它域名（`https://gh-proxy.com/https://api.cloudflare.com/...`
直接返回该服务的 404 页）。

### 猜测阶段的三次踩空

拿不到数就只能猜，而猜的方向一路被外力纠正：

1. 先怀疑 `list()` 的全表扫描 —— `kv` 表的 `list` 写的是
   `WHERE key LIKE 'x%' ORDER BY key`，SQLite 没索引时会整表扫，按扫描行数计费。
   这条最像真的，而且手头那张「每请求 8 次 D1 查询」的曲线也对得上。
2. 顺着这条线去找热路径，**结果发现了 `sites.js` 的 `getSite()` 与 `listSites()`
   都有进程内缓存**，于是这条假设不成立 —— 这一步本该在动手改代码之前就先确认。
3. 又怀疑是 `geoip:<ip>` 永久缓存无限累积，把行数撑起来了。

三条都拿不出证据。真正的事实后来是这样的：

| 出事的那两天（9-18 / 9-19） | 数字 |
|---|---|
| D1 rows read | **5,092,939 / 5,227,526**（免费限额 500 万/天，超出 2% 和 5%） |
| D1 rows written | 7,698 / 69（限额 10 万，完全没到） |
| 整个库 `file_size` | 520,192 字节（限额 5 GB） |

**爆的是行读取总数，不是存储，也不是写入。** 三条猜测没有一条命中 ——
尤其第 3 条：整个库才 520 KB，行数再多也谈不上「撑破」。

### 最终是怎么拿到数的

沙箱连不上 CF，但 **GitHub Actions 的 runner 网络不受这个限制**。做法是：

1. 起一个临时分支，workflow 里让 runner 用仓库既有的 `CLOUDFLARE_API_TOKEN` 调 CF。
2. **结果写回另一个分支**（如 `diag/d1-result`），本机再用 git 通道 fetch 回来读。
   之所以不用日志：gh-proxy 会挡「非资源下载」，`/actions/jobs/{id}/logs` 取回来的
   只有一句 `Web page content is not allowed`。结果也**不能推回同一个分支** ——
   那里挂着 `on: push`，推一次就把自己再触发一遍，无限循环。
3. 用完删掉 workflow 与两个分支（`git push --delete`；注意 PAT 没有删除 ref 的权限，
   走 REST API 那一路会 403，得用 `git push --delete`）。

### 沉淀

- **先花预算取数，再花预算改代码。** 「看着像」的理由越合理，越容易跳过验证 ——
  尤其当它还跟你手头的曲线吻合的时候。这次三条猜测全部落空：
  按第 1 条去给 `list()` 加索引的话，改完发布，下一个流量尖峰照旧打脸，
  而你会以为是「没改对」。
- **第三方 API 的字段名不要猜，用内省问。** `d1AnalyticsAdaptiveGroups` 的实际字段是
  `rowsRead` / `rowsWritten` / `readQueries` / `writeQueries`，
  没有 `databaseName`（猜它是第一次运行失败的直接原因）。花一次请求换准确的字段名，
  比廉价地试错几轮便宜。
- **自适应分组返回的是采样桶，不是按天汇总。** `limit: 30` 就是 30 个桶，
  直接打印会把「某个分钟的值」误读成「当天的值」。必须按 `(databaseId, date)`
  二次聚合，否则结论可能差一个数量级。
- **查询时间跨度有硬上限**（实测 4w4d），45 天会被 `code: quota` 拒掉。
- **用量曲线自身就是降级的证据**：9-15 / 9-16 有 46k Worker 请求，
  D1 rows read 却只有 1.2 万 / 11.6 万 —— 说明那时已经在内存模式里跑，
  请求根本没转化成存储读取。也就是说，**用量的塌陷本身就是降级已经发生的证据**：
  看不到 D1 消耗，不代表没出问题，很可能恰恰是出问题之后的常态。

> （这里是 GitHub runner），而不是退回去靠猜。

## 33. D1 被打爆的真凶：`key LIKE 'x%'` 让每次 list 都扫整张表

### 现象

2026-09-18 当天 `any-proxy-db` 的 rows read 打到 **5,092,939**（免费计划每日上限 500 万），
站点自动降级到内存模式，主订阅与临时订阅**同时失效**。9-19 继续 5,227,526。

一开始的判断全部不着边际：猜 `list()` 全表扫描（对了方向，但随即否定）、猜热路径没缓存、
猜 `geoip:<ip>` 无限累积。三条全错（过程记在第 32 条）。

### 取到真数之后

绕道 GitHub Actions runner 调 CF REST，拿到两个决定性的数字：

```
SELECT COUNT(*) FROM kv   →  n = 2994，meta 里 rows_read = 2994
size_after = 528384
```

于是可以反算：

| 量 | 值 |
|---|---|
| kv 表行数 | 2,994 |
| 9-18 rows read | 5,092,939 |
| 9-18 readQueries | 79,660 |
| 单次查询平均读行数 | 5,092,939 ÷ 79,660 ≈ **64** |

大部分查询是主键精确定位（`WHERE key = ?`，一行就是一行）。要平均到 64，
只能是另一种查询在混：**每次约 3,000 行**。

`5,092,939 ÷ 2,994 ≈ 1,701`，也就是那天大约发生了 **1,700 次整表扫描**，
而 `readQueries` 里它只占 2% —— 2% 的查询贡献了几乎 100% 的超额。

### 原因

`src/storage.js` 的 `list()` 是这样写的：

```sql
SELECT key FROM kv WHERE key LIKE ? ORDER BY key LIMIT ?     -- 参数 'site:%'
```

表结构里 `key TEXT PRIMARY KEY`，索引 `idx_kv_key ON kv(key)` 也是默认的 BINARY collation。
而 SQLite 的 LIKE 优化有个前提：**索引的 collation 必须与 `case_sensitive_like` 匹配** ——
`case_sensitive_like` 默认关闭，此时要求索引是 `COLLATE NOCASE` 才能把 `LIKE 'x%'`
改写成范围条件去走索引。我们的索引不是，于是优化不生效。

真跑一遍 SQLite（`EXPLAIN QUERY PLAN`，同份数据 2993 行）：

| 写法 | 执行计划 | 代价 |
|---|---|---|
| `WHERE key LIKE 'site:%'` | `SCAN kv USING COVERING INDEX idx_kv_key` | 扫满 2,993 行 |
| `WHERE key >= 'site:' AND key < 'site;'` | `SEARCH kv USING COVERING INDEX (key>? AND key<?)` | 读 1 行 |

注意它是 `LIMIT 1000` 也一样 —— 匹配项可能排在表尾，扫描不会提前结束。

**这条 bug 最难的地方在于：它不影响正确性。** 扫全表和查索引返回完全相同的结果，
差别只在计费的那一行数字上。所以所有「看返回值」的测试都是绿的，
上线之后也看不出任何异常，只在月底账单/配额爆掉时才现形。

### 修复

把前缀匹配改成范围比较，`list()` 按 `key >= prefix AND key < upperBound(prefix)` 查：

```js
const upper = prefixUpperBound(prefix);   // 'site:' -> 'site;'（末字符码位 +1）
```

边界的安全退让写在 `prefixUpperBound()` 里，这几处是刻意的：

- 空前缀返回 `undefined` → 走无上界分支 `WHERE key >= ?`（「列出全部」不能带上界）。
- 末字符是**代理项**（emoji 的半边）或已达码位上限时返回 `undefined` → 放弃优化。
  代理项 +1 会得到另一个无效半边，无法保证落在目标字符串之后 ——
  **算小了会漏键，而漏键比慢一点严重得多**。

顺带修掉一个从未被发现的行为错误：前缀里含 `_` 或 `%` 时，LIKE 会把它们当通配符。
查前缀 `A_` 时旧写法会把 `APP_CONFIG`、`Aab`、`Ab` 一起捞出来
（pattern `A_%` 的第 3 个字符是任意字符）。

### 沉淀

- **成本 bug 不在返回值里，所以必须盯执行计划。** 这次的判据是 `EXPLAIN QUERY PLAN`
  里必须出现 `SEARCH` 而不是 `SCAN`。只看返回结果的测试在这条退化面前是恒绿的。
- **检查不能誊一份 SQL 过来比对。** 第一版 `check-d1list.mjs` 正是在脚本里重写了一遍
  新旧 SQL —— 结果「把实现改回全表扫描」时检查**全绿通过**。`tooth-d1list.mjs` 当场
  把这个漏洞抓了出来（7 个变异漏了 3 个，全是这条 SQL 的）。
  正确做法是：`createD1KV()` 接一个假的 `db` 句柄跑真 SQLite，**断言实现实际下发的那条 SQL**。
  写成本高一些，但这是唯一能让检查咬得住的写法。
- **边界算不出来时要显式退让，不能猜一个。** 遇到算不出安全上界的输入，宁可全扫
  也不能凑一个数 —— 而且这个退让本身要有专门的断言盯着（emoji / 末字符达上限两个用例）。
- **不要手算期望值。** 断言里写死了「'站点' + 1 = '站奀'」，
  实际是 '站為' —— 期望值交给代码算，别手打。
- 这一类问题值得单独开一个 check 而不是塞进大的那个：它需要 python 进程、
  需要铺几千行数据，跑起来比别的慢，混在一起会拖慢整套。

> 沉淀进 `AGENTS.md` 第 5 节：性能/成本类约束的执行判据不能只看返回值。
