# 07 · 踩坑记录

按**犯错的代价**排序，不是按时间。每条都能复现，每条都是真踩过的。

---

## 1. Response body 一旦读取就 locked，客户端拿到空壳

**现象**：某些分支下页面白屏 / 资源 0 字节，但状态码是 200，服务端日志也不报错。

**原因**：先 `await response.text()` 读了 body，之后某个分支决定「不处理、原样返回」，
于是把这个已经 locked 的 response 直接返回 —— body 读不出来，客户端收到空壳。

```js
// ❌ 读过之后这个 response 已经不能再读第二次
const text = await upstream.text();
if (跳过处理) return response;

// ✅ 按原文重建
return new Response(text, { status: response.status, headers: response.headers });
```

**修**：订阅处理链路抽了 `passthrough(resp, original, status)`，所有「读过才决定放弃」的分支
统一走它重建。

**教训**：响应体是一次性资源。任何「先读再判断」的写法，都要保证每个出口要么消费读到的数据，
要么用它重建。

## 2. `atob` / `btoa` 只认 Latin-1，毁掉整份订阅

**现象**：`"vmess节点"` 变成 `"vmessèç¹"`；`btoa` 遇到中文直接抛 `InvalidCharacterError`。

**代价**：**最高**。这不是显示问题，它会让整份订阅内容损坏、客户端全部连不上。

**修**：抽 `b64DecodeUtf8` / `b64EncodeUtf8`，所有涉及订阅 / vmess JSON 的路径都走它。

**教训**：涉及二进制 <-> 文本的转换，先问一句「字符集是什么」。

---

## 3. VLESS 的 UUID 是 16 字节二进制，不是 36 字符串

**现象**：WebSocket 握手 101 成功，但之后服务端完全不回包。

**原因**：把 36 字符的 UUID 字符串直接塞进 header，整个协议头错位，服务端解析失败后静默断开。

```python
# ❌
uid = uuid.encode()
# ✅
uid = uuid_.UUID(uuid).bytes   # 16 字节
```

**教训**：「握手成功但数据不转发」这个症状太容易被解读成节点坏了。协议层的错位不会报错，
它只是沉默。

---

## 4. L4 判据写在 try 里，异常时被吞掉，健康节点全被判死

**现象**：79 个节点全部显示「WS ok，但 VLESS 转发无回包」，看起来像节点全坏。

**原因**：服务端回完数据会发 WS close 帧然后收尾。脚本拿到完整响应后**继续傻等到填满 3000 字节**，
第二次 `recv` 超时抛异常，而判定 `if "HTTP/" in buf` 写在 `try` 内部 —— 被 `except: continue`
直接跳过，**已经收到的有效数据随之丢弃**。

**修**：判定移到异常之外；收到响应头就跳出，不傻等；把「超时」当作「收完了」而不是「失败了」。

**代价**：给出了完全错误的结论（「你的代理节点几乎全不可用」），差点引导删掉健康的优选池。

---

## 5. `b"101" not in <str>` —— 字节串与字符串混用

**现象**：同上，所有节点 L3 再也上不去。

**原因**：Python 里 `bytes not in str` 直接抛 `TypeError`，而调用方是 `except Exception: continue`。

```python
# ❌ TypeError
if b"101" not in buf.split(b"\r\n", 1)[0].decode("utf-8"):
# ✅
head = buf.split(b"\r\n", 1)[0].decode("utf-8", "replace")
if "101" not in head:
```

**教训**：宽泛的 `except` 会把 bug 变成「看起来正常的失败」。宁可让异常炸出来。

---

## 6. 同一条 WS 连接上重试第二个目标，会连累全部目标

**原因**：WS 握手一次只能携带一次 VLESS 首包。在同一连接上重试第二个目标时，
服务端已经把它当作上一个流在收 —— 第一个失败时后面全部跟着失败。

**修**：每个探测目标 **新开一条连接**。

---

## 7. 用 Cloudflare 托管的站点当探测目标，会把健康节点判成坏的

**现象**：选了 CF 托管的域名做转发判据，节点全部「失败」。

**原因**：CF 对自己边缘 IP 发来的明文 HTTP 请求会直接回 400。这是目标侧行为，不是节点问题。

**修**：改用非 CF 托管的站点（`httpbin.org` / `www.baidu.com` / `www.qq.com`）。

**教训**：做端到端判据时，先确认判据本身一侧中立方。

---

## 8. 跨模块改函数签名，没顺调用链检查 → 全站 502

**现象**：`ReferenceError: env is not defined`，每个代理页面 502。

**原因**：`proxyRequest` 加了 `env` 参数，中间层 `dispatchProxy` 没跟着传。
而所有单元测试**全绿**（它们都没走完整链路）。

**修**：改调用链 + 新增 `tools/check-smoke.mjs`，从 `handleRequest` 进入做集成测试。

---

## 9. 两份缓存共用 key，产物互相串

**现象**：Turbo 的局部更新拿到一整份 docWrite 包裹的文档。

**原因**：`cachedHtmlRewrite` 与 `cachedDocWritePage` 用了完全相同的 key，
而两条分支的产物完全不同。

**修**：key 加命名空间 `rw|` / `dw|`。

---

## 10. path 的 `%2F` 不能 URL 解码，也不能不解码 —— 要按场景

这是本项目**唯一一次被自己的注释误导**：

- 注释写着「path 必须原样发出，百分号解码会让服务端匹配不上」
- 照做后发 `GET %2F` → **400 Bad Request**
- 改回 `parse_qsl`（会解码）发 `GET /` → 握手正常

真相是：订阅里写作 `path=%2F`，而 HTTP 请求行必须是 `GET /`。**注释是错的，断言要先验。**

**教训**：代码注释里的断言也是需要检验的。特别是当注释里出现「必须」「绝不能」时。

---

## 11. GeoIP 对 CDN 任播 IP 给不出/给不准国家

**现象**：67 个 IP 里只有 33 个有标注（49% 覆盖），主力 CF 优选节点全都没名字。

**真相**：三个数据源给出三个答案（主源查不到 / ip-api 说加拿大 / ipwho.is 说美国）。
任播 IP 本来就没有单一地理归属。

**取舍**：不编国名。查到就显示真实国家，查不到但命中 CF 官方段就标 `Cloudflare 任播`。
详见 [01-需求与迭代](./01-需求与迭代.md) 迭代 4。

**教训**：当一个「数据源问题」看起来可以靠加数据源解决时，先确认是不是**前提本身不成立**。

## 12. `pkill -f local-dev.mjs` 把自己的 shell 也杀了

**现象**：命令返回 `Signal: SIGTERM`，后续命令全部没执行。

**原因**：`pkill -f` 匹配的是完整命令行，而当前 bash 的命令行里就包含这个字符串 —— 自杀。
用方括号技巧（`local[-]dev`）也不够，因为同一条命令后面还要启动它。

**修**：按监听端口找 PID 再 kill：

```bash
ss -ltnp | grep ':8787' | grep -oE 'pid=[0-9]+' | cut -d= -f2 | xargs -r kill
```

**教训**：起后台测试服务时，kill 和 start 要分两条命令执行。

## 13. 本报告自身的坑：并行写代码时的字符污染

写这批文档的过程中，`架构设计 / 开发规范 / 测试体系 / 部署上线 / 运维`几份都出现过
输入法残留导致标题或列表里混入外来字符的情况，全部靠写完立刻回读才发现。

**教训**：生成大段文本后必须**回读校验**。最容易被污染的是标题和列表的首行 —— 那里既显眼
又不会被拼写检查覆盖，一旦入库就很难再被搜出来。

## 14. 配置有两个入口：面板上改了，线上跑的却是环境变量

**现象**：面板里把「只保留边缘网络内的候选」关了，保存提示成功，订阅里的候选数量没变。
翻代码才发现这个开关**面板上根本没有** —— 它只认 `env.SUB_STRICT`，而面板里那个
「同名开关」是另一个模块的、控制的是别的东西。

**根因**：同一个业务设定被拆成了两套入口 —— 一部分参数进了面板 SPEC（KV 可改），
另一部分只认环境变量。两套都是「对」的，所以：

- 不报错：面板保存成功，接口返回 200；
- 不冲突：环境变量与 KV 是两条互不相干的取值路径；
- 单测全绿：每个模块自己测自己都对；
- **但运营者永远改不到，而且看不到** —— 只能翻 `wrangler.toml` 猜线上在跑哪个值。

而且这类参数改了**要重新部署才生效**，这跟「面板保存即生效」的直觉正好相反，
排查时极易往错误方向找（先怀疑缓存、再怀疑没保存）。

**修**：面向运营的参数一律收进 `src/settings.js` 的 `SETTINGS_SPEC`，一处声明：
面板表单从它渲染、运行时从它取默认值、手册从它生成。留一条静态规则
（`check-single-source.mjs`）堵住回退 —— 除 `settings.js` 自己以外，
**任何模块直读 `env.XXX` 直接变红**；再补 `check-settings.mjs` 端到端真跑
「渲染 → 保存 → 立即生效」。

**教训**：判据不是「代码里有没有写死的常量」，而是**同一个设定有没有两份定义**。
两份定义不会报错，只会让「改了没反应」变成一个查不出原因的谜。

## 15. 面板改了节点配置，订阅毫无变化：引擎每次请求都覆盖自己的配置文档

**现象**：在面板改「节点 ID / 节点地址 / 节点路径」，保存提示成功；清空浏览器缓存、
换客户端、重开订阅，输出里的节点还是老样子。

**根因**：这几个字段的存储是**代理引擎自己的配置文档**（KV 里的 `config.json`）。
面板写入的确实是它，一点没写错 —— 但 `vendor/vless.js` 每次请求都会用**环境变量与
请求上下文**再覆盖一遍自己这份文档：

```js
userID = (envUUID && uuidRegex.test(envUUID)) ? envUUID.toLowerCase() : 由口令派生
```

于是面板值与运行时值成了两条路：面板改的是「文档」，引擎认的是「环境变量」。
两条路都自洽，所以面板保存成功、接口 200、配置确实落了库 —— 只是没人读。

还有两个由此衍生、更难发现的变体：

- 填了一个「看起来像 UUID 但不是 v4 形态」的值 → `uuidRegex` 不匹配 → 引擎**默默**
  改用派生 UUID。面板说保存成功，实际节点 ID 完全没变。所以格式判断必须与引擎的
  正则逐字一致，并且要在**写入前**拦住（见 `util.js` 的 `isUuid` + 注册表的 `validate`）。
- 把节点地址清空 → 面板写入空数组 `[]`，而引擎的兜底是 `if (!config_JSON.HOSTS)`，
  空数组是**真值** → 兜底不触发 → 节点地址变成空。清空必须**删掉这个键**，不能写 `[]`。

**修**：把有效值回灌成引擎认的环境变量（`settings.js` 的 `engineEnvFor`），
让「面板 → 存储 → 引擎」成为一条链；注册表里这类字段标 `store: 'engine'`，
读改写整份文档以保留引擎的其它键；清空走 `writeEngineField`（空数组 → 删键）。

**教训**：保存成功 ≠ 生效。「存储里有没有值」和「运行时读的是不是它」是两个问题，
面板只验证了前者。

## 16. 面板改了标注样式，订阅输出没变：取值分了两份

**现象**：面板上把节点备注的国家标注从「中文代码」改成「旗帜」，保存成功，订阅里的备注没变。

**根因**：「标注开关 + 样式」这两个值被解析了两遍：

- 面板写入的那条路写进 KV；
- 订阅输出那条路（`nodetag.js`）**只读环境变量**，压根没看 KV。

两处都能跑、都不报错，只是读到的东西不同。修的时候还顺带发现第三个名字：
旧实现把数据源标注成 `'kv'`，而面板只认 `panel / env / default / legacy` ——
连「这个值从哪来」都各说各话。

**修**：取值只留 `readSettings` 一条路，归因只留 `settingsSource` 一处；
`styleFrom` 变 async（要 await 注册表），调用链全部跟着 await。
`check-nodetag.mjs` 里补了「没有面板值时回落到环境变量种子」和「清掉面板值后回到环境变量」
两条回归，把三级取值钉住。

**教训**：同一个设定的**读取入口**也必须只有一个。「写在哪里」统一了还不够 ——
读取侧只要还留着一份自己解析的实现，就会继续对不上。

## 17. 「保存成功」而值没变：写入侧把不认识的字段静默忽略

**现象**：接口调通、返回 200、提示「已保存」，但配置项的值一个都没变。

**根因**：`saveSettings` 只遍历 `SETTINGS_SPEC` 里的字段（`if (!(key in patch)) continue`），
**认不出来的键直接跳过**。于是只要字段名对不上——写错一个字母、或者某个调用方还在用旧别名
`{enabled, style}` 而注册表里叫 `node_tag_enabled` / `node_tag_style`——结果就是：
不报错、不抛异常、日志干净、返回体还是「已保存」。

这是第 14 条的续集：**入口**统一了，**写入侧**还留着一个静默的漏斗。

**修**：不认识的键直接 400 并点名是哪个字段：

```
未知配置项：enabled、style（字段名以 settings.js 的 SETTINGS_SPEC 为唯一真源）
```

顺带把一条原本写成 `400 或者 200 但没写进库都算过` 的断言收紧成硬要求 ——
那种「两种都算过」的断言等于没查，恰恰放过了这个 bug。

**教训**：凡是「静默忽略」的分支都要问一句「忽略之后，调用方能不能知道」。
不能让调用方知道，就等于把错误藏进了「一切正常」里。

## 18. 同一个配置长在所有选项卡里：表单是手写的，不是从目录渲染的

**现象**：「优选池 / 健康检查」的卡片在每个选项卡下都出现；「订阅链接」和「节点国家标注」
两张卡片，字段、控件、帮助文字跟别处都不一样 —— 因为它们是在页面模板里**手写**的。

**根因**：接口目录（`api-catalog.js`）只驱动了「配置页」的渲染，归属功能选项卡的那部分
不在配置页出现，于是这些页面的卡片只能各写各的 HTML 与保存脚本。
手写一份的代价：新增一个动作要在页面里再加一段 `onclick`；改一个字段要在两处同步；
某个选项卡忘了套统一的容器类，它的输入框就比别处窄一圈。

**修**：给字段加 `panel: '<目录项 id>'` 投影标记（一个字段只能投到一张表单），
页面模板里只写 `settingFormById('node-config')`；选项卡自己的动作按钮改由
`toolItemsForTab('<tab id>')` 从目录渲染，目录项用 `body` 声明固定请求体。
`check-configui.mjs` 第 4 段钉住「同一份配置全页只有一张可编辑表单」。

**教训**：只要界面上还有手写的第二份，它迟早会和真源分叉。判断标准不是「有没有界面」，
而是**界面是不是从真源渲染出来的**。

## 19. 开了部署压缩后，面板一直「加载中」、按钮全失灵：注入脚本靠全局名传数据

**现象**：给 `wrangler.toml` 加上 `minify = true` 压掉 38% 体积，部署成功、首页正常，
但一进「CF 用量」「访问统计」两个面板就卡在加载态，按钮点了没反应。刷新、换浏览器都一样。
Worker 侧的日志**一条错误都没有**。

**根因**：这两个模块的前端脚本是「写成本地函数、再用 `toString()` 注入浏览器」的，
数据靠这样一段带过去：

```js
`${KEEP_NAMES_SHIM}var CF_TREND_METRICS=${CF_TREND_METRICS_JSON};(${cfInit.toString()})();`
```

前半段的 `CF_TREND_METRICS` 是**硬编码的字符串字面量**，后半段函数体里引用的
`CF_TREND_METRICS` 是**模块级标识符**。不压缩时两者同名，一切正常；开了 minify 之后
模块级标识符被重命名成一个字母，字面量还是 `var CF_TREND_METRICS=` —— 名字对不上，
注入到浏览器的脚本**第一行就 ReferenceError**，整段中断。

之所以查不出来：错误发生在**浏览器**里，Worker 侧完全无感；而本地 20 套自检跑的是
**源码**（不压缩），源码层面这两个名字当然是同一个，所以全绿。

**修法**：数据改成**实参**传入，不依赖全局名：

```js
`${KEEP_NAMES_SHIM}(${cfInit.toString()})(${CF_TREND_METRICS_JSON}, ${CF_STATUS_KLASS_JSON});`
```

函数体和调用处属于同一次压缩产出，命名必然同步，天然免疫重命名。
`tools/check-minify.mjs` 钉住这条纪律（并做了牙齿验证：把旧写法加回去，它确实变红）。

**教训**：**产物形态变了，源码层面的自洽就不作数了。** 凡是把源码当字符串送出去的地方
（`toString()` 注入、模板拼接、代码生成），都要假设标识符会被改名，只能依赖
**同一份产出的内部结构**，不能依赖名字本身。另外——本地自检跑的是源码，压缩产物的
问题它一条都抓不到，这类改动必须有专门针对产物的检查。
