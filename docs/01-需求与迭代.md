# 01 · 需求与迭代

按时间顺序记录每一轮需求的来源、取舍和验收标准。这里的取舍大多是有争议的——把当时为什么
选 A 不选 B 记下来，免得半年后有人重新纠结一遍。

---

## 迭代 1：浏览器优选修复

**来源**：面板「立即更新优选 IP」点了就超时报错。

**根因**：优选候选原本只从一个本地池里取，没走订阅链接，取不到候选就直接卡死。

**方案**：候选来源改成多级降级 —— 已验证可用集 `GOOD_IPS` → 优选池 `PREF_IPS` → 订阅链接里的节点
（按边缘 IP 段过滤）→ 候选域名池 `PREF_DOMAINS` 动态解析。

**验收**：面板点「立即更新优选 IP」能跑完并写回结果，不超时。

---

## 迭代 2：首页伪装

**来源**：默认首页会把「这是个代理 / 订阅服务」写在脸上，任何扫站的都能一眼认出来。

**方案**：根路径按访客分三档出不同内容（详见 [02-架构设计](./02-架构设计.md)），
陌生人看到的是一个普通站点模板，面板挪到隐蔽入口。

**关键取舍 —— 严格到什么程度？**
选择的是「陌生人访问一切都返回 404，包括路径不存在时」。代价是牺牲了友好的错误提示，好处是
**302 的 Location 头不会再泄露 `/__admin` 这类面板命名空间**。这个取舍是被实测逼出来的：
早期版本对不存在的面板路径返回 302 到登录页，Location 里明明白白写着面板路径，伪装等于白做。

**验收**（实测通过）：

```
根路径          → 200，「站点维护中」，页面内搜索 __admin / __api / Any-Proxy 零命中
/__admin        → 404
/__api/sites    → 404
/site-status    → 302 + Set-Cookie: visited=1（进门）
带 cookie 再访根 → 200，正常显示管理面板
```

## 迭代 3：节点备注标注 IP 归属国家

**来源**：订阅拉下来几十个节点，备注全是「CF 电信优选」，看不出落在哪个国家。

**需求原文要点**：「可以**配置**是否需要加」「获取国家名称使用**效率最高**的方法」。

「效率最高」具体落成五条，这是本轮的核心：

1. **批量** —— 一次 POST 问 100 个 IP，80 个节点 = 1 次外部请求
2. **永久缓存** —— IP 归属几乎不变，同一个 IP 第二次起零外部请求（这是最大的一笔节省）
3. **负缓存** —— 查不到的也缓存，避免同一个 IP 每次订阅都白问一轮
4. **零数据表** —— 中文名走 `Intl.DisplayNames`，国旗 emoji 由 ISO 3166-1 直接算出，都不需要内置映射表
5. **异步写** —— 缓存写入甩到 `ctx.waitUntil`，不让存储往返拖慢订阅返回

**验收**：81 个节点拉下来，IP 节点备注形如 `CF 电信优选 | 美国【US】`；第二次拉取耗时从 3.3s 降到 1.6s。

## 迭代 4：CDN 任播 IP 的归属问题（本轮最重要的取舍）

**来源**：迭代 3 上线后实测，67 个去重 IP 里只有 33 个有标注，覆盖率 49%。

**查出来的真相**：

| 分类 | 数量 | 主源 GeoIP 覆盖 |
|---|---|---|
| 非 CF 段的普通 IP | 25 | **23 / 25 = 92%** |
| CF 官方 IP 段内 | 42（占 63%） | **10 / 42** |

主力节点（CF 优选）恰好全是查不到的那一批。更要命的是，对同一批 CF 任播 IP，三个数据源
给出三个不同答案：主源 `api.country.is` 查不到、`ip-api.com` 说加拿大、`ipwho.is` 说美国。

**这不是谁准谁不准的问题** —— CF 任播 IP 是同一个 IP 在全球边缘通告的，**本来就不存在
单一地理归属**。当初选「照 GeoIP 显示国家」时隐含的前提对这些节点不成立。

**候选方案与取舍**：

| 方案 | 覆盖率 | 为什么否掉 / 为什么选它 |
|---|---|---|
| **GeoIP 优先 + CF 官方段兜底**（选定） | ~97% | 查到就显示真实国家；查不到但命中 CF 官方段 → 标 `Cloudflare 任播`。**零错误标注**。段列表走官方源拉取并长期缓存，之后每个 IP 判定是纯内存 CIDR 匹配、零外部请求，依然满足「效率最高」 |
| 加 ip-api 后备源硬补 | 94% | 会把 CF 节点标成「加拿大【CA】」这类很可能是错的国名；且免费版只有 HTTP 明文、限速 15 次/分钟要切成小批慢慢跑 |
| 维持现状 | 49% | 标出来的都可信，但订阅主力全都没名字 |

**决定**：宁可少写一个国名，也不给用户一个错的。这是贯穿本项目的判断原则。

**验收**：33 项自检全通过，含「CF 节点标任播」「普通节点标国家」「重复处理幂等」。

## 迭代 5：性能 —— 出口压缩与对冲请求

**来源**：「尽可能提升代理网站的访问速度」。

**定位到的头号瓶颈**：反代正文链路是「上游压缩 → Worker 读 body 解压 → 改写 → **明文输出**」。
解出来的明文不再压缩，浏览器收到的就是原始体量 —— 几百 KB 的 JS bundle 全裸奔。

**实测收益**（Worker 侧压缩后）：

```
45378 B → 7653 B    降到 17%
```

本地 fixture 实测同一份主文档：`32013 B → 7949 B`，降到 25%，且 gzip 解压后与明文逐字节一致。

**第二个优化 —— 对冲请求（hedged request）**：先发一个，超过阈值没回来就并行发第二个取快的。
治的是长尾延迟（P99），只对幂等请求启用（GET/HEAD 且无 body）——重复提交一次带 body 的 POST
可能造成重复下单，那种风险换来的延迟收益不值。

**第三个 —— 重试不再空等**：原先失败后 `sleep(300ms)` 再重试，两处就是 600ms 纯等待。
这段时间里 Worker 照样占着 CPU 预算，而上游不会因为 300ms 就恢复。去掉后失败路径直接省掉这 600ms。

## 迭代 6：主页元素精简

**来源**：管理面板四块内容堆在一屏，太长。

**方案**：顶部标签导航（站点 / 代理节点 / 优选 IP / 伪装与安全），当前分区记在 URL hash。

**关键取舍**：采用**最小侵入** —— 不改 HTML 结构、不销毁元素、不动任何既有 id 和 JS 逻辑，
只加 `data-pane` 标签做显隐切换。把回归风险压到最低，代价是 DOM 里还留着未激活分区的元素。
对这种纯展示型改动，这个代价是划算的。

## 迭代 11：配置统一化（能配的都搬到面板上）

**来源**：一条直白的诉求 ——「统一所有配置，除了必须固定的部署形态项，其他所有配置都必须
可以在页面做配置，且实时生效」。

**问题**：面板其实早就有一套完整的配置层（SPEC + 注册表渲染表单 + 三级取值），但它只覆盖了
一部分。另一部分参数**只认环境变量**：`SUB_STRICT`、`SUB_CANDIDATE_LIMIT`、`DNS_BUDGET_MS`、
`DNS_SETTLE_MS`、`MAX_PROBE_LIMIT`、`PROBE_CONCURRENCY`、`PROBE_TIMEOUT_MS`、
`PROXY_HEDGE_MS`、`GEOIP_BATCH_SIZE`、`GEOIP_BATCH_URL`、`CF_NETS_URL`、
`CF_API_TOKEN / CF_ZONE_ID / CF_API_EMAIL / CF_API_BASE`、`PREF_RANGES_URL`、`DOH_URL`、
`STATS_SALT`、`GH_ACTIONS_URL`、`WORKER_SCRIPT`、`DNS_INTERVAL`、`POOL_LIMIT`、
`DOMAIN_POOL_LIMIT` 等 20+ 项。

这不是「界面没做」的问题，而是**改了要重新部署才生效，而面板上又看不到它** ——
运营者只能翻 `wrangler.toml` 猜线上到底在跑哪个值。

**方案**：新建 `src/settings.js` 作为「面向运营的参数」的唯一真源（`SETTINGS_SPEC`，31 个字段、
5 个分组），一处声明、三处消费：

1. **运行时** —— `readSetting(env, key)` / `readSettings(env)`，取值仍走三级降级；
2. **面板表单** —— `api-catalog.js` 的目录项带 `spec/params`，`config-ui.js` 按注册表渲染，
   **不手写任何控件**（`gridHtml` 新增按 `section` 分段的能力，用来在卡片里分小标题）；
3. **操作手册** —— `gen-manual.mjs` 从同一份生成速查表附录。

**实时生效**：`writeSection` 写库后调 `notifyConfigChange(section)` 广播，
各模块用 `onConfigChange` 注册清缓存的钩子（`cf-analytics.js` 的 `cache.clear()`、
`geoip.js` 的 `cfNets = null`）。因此**下一次请求**就按新值跑，不需要重新部署。

**明确排除在外的（部署形态，不是运营参数）**：

| 项 | 为什么不能进面板 |
|---|---|
| `STORAGE_BACKEND / DB / SITES / MEDIA_R2` | 改它等于换存储后端，必须和 `wrangler.toml` 的绑定同时改 |
| `PASSWORD / KEY` | 是凭据而非配置，混进 KV 只会多一处泄漏面 |

**平滑迁移**：历史遗留的独立 KV 键（`DNS_CONFIG` / `SUB_URL` / `CF_IP_RANGES`）通过
`field.legacyKey` 兜底 —— 升级后首次读取时若新键为空而旧键有值，就把旧值迁过来，
避免出现「面板显示默认值、实际沿用旧值」。

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 不做「一次性硬编码表单」，全部走注册表 | 手写表单就意味着「加一个参数要改三处」，而这三处迟早会不一致（`check-configui` 就是为此而生） |
| 密钥类字段只回显「是否已配置」 | 与告警 Webhook 同一套理由：它是一条凭据，回显明文等于多一个泄漏点 |
| `cf_ip_ranges` 的空值视为有意义（`NO_EMPTY_OVERRIDE`） | 「清空 = 回到内置默认段」与「清空 = 用默认值」在这里语义不同，前者是常见操作 |
| 环境变量继续保留为「首次部署的种子」 | 不破坏既有部署习惯；只是不再是唯一入口 |

**验收**：新增 `tools/check-settings.mjs`（51 项）端到端真跑「渲染表单 → 保存 → 立即生效」，
并覆盖密钥脱敏、清空回默认、遗留键迁移、环境变量种子、静态扫描；
`check-single-source.mjs` 新增「运行参数禁止直读环境变量」规则（唯一放行 `settings.js`）。
按 AGENTS 第 5 节做了牙齿验证：故意还原旧写法（直读 `env.SUB_STRICT`、漏挂 ops 组、
上限用错常量），确认三套检查都变红。

## 迭代 12：节点延迟实测 —— 把「能通」升级成「多快」

**来源**：用户从「还能集成什么」的清单里选了节点延迟实测。背景是一个一直存在但没人说破的
问题：优选 IP 的判定只有**二值**（连得上 / 连不上），从来不问快慢。

**问题**：`dns.js` 的 `filterUsableIps` 并发探测后按「哪个协程先摸到」收结果 —— 顺序近似随机。
于是「优选」选出来的常常只是**恰好先返回**的那一个，而不是最快的那一个。探测能通、
接口返回 200、统计数字也都有，唯独顺序不对，这种问题从任何单个模块看都是「对的」。

**方案**：新增 `src/latency.js`：`measureTargets(targets, probeFn, opts)` 对每个候选多次取样 →
取中位数 → 按延迟升序返回。默认关闭：`filterUsableIps` 只在 `opts.sortByLatency` 为真时走
延迟路径，否则行为与加之前**逐字节一致**（老调用方零改动）。

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 不 `import` `dns.js`，探测函数由调用方注入 | `dns.js` 是它的唯一调用方，直接 import 就成循环依赖了 |
| 单次失败不算失败 | 抖动就误杀的代价是**少一个可用节点**，比多等一次贵得多 |
| **不看状态码** | 伪装模式下未登录访问 `/__api/api-config` 就是 404 —— 那恰恰说明这个 IP 通 |
| 取中位数而不是平均值 | 一次偶发的长尾就把均值拉偏；中位数对单次尖刺免疫 |
| 默认关闭 | 探测要花时间。交给调用方按场景决定，不替所有调用方付这份成本 |

**验收**：新增 `tools/check-latency.mjs`（26 项）。排序用例**刻意用串行**——并发下快的自然先完成，
顺序天然就对，那样测不出去掉 `.sort()` 的情况。另钉住两条：单次抖动不能误杀、
伪装下的 404 必须算通。CI 新增「节点延迟实测校验」一步。

### 第二次接：把快慢排到**订阅**上

第一次接完之后，延迟数字有了、面板也能看，但用户体感一点没变 —— 因为**顺序没落到客户端
真正用的地方**：客户端通常拿订阅里第一个节点，而 `/sub` 吐出去的顺序还是上游订阅的原文顺序。
延迟实测于是只是个能看的数字，不是速度。

**方案**：新增 `src/sublat.js`，在**订阅出口**做重排 —— 节点由 vendor 引擎生成，我们在它吐
出来之后按实测延迟重排，与 `nodetag.js` 补国家标注同一层、同一套取舍（不动 vendor、
开关一关就是原样透传）。新增两个运行参数：`sub_latency_sort`（默认开）、
`sub_latency_ttl_ms`（默认 30 分钟）。

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 排序放在出口，不改 `vendor/vless.js` | 节点由它生成；上游升级时不冲突，关掉开关就是原样透传 |
| 测量结果按 TTL 存 KV，**多个客户端共享** | 否则每次拉订阅都要实测一遍，几秒的延迟会落到每个客户端头上。只有缓存过期后那一次拉取多花几秒 |
| 不通的记 `null` 而不是 `0` | `0` 会被当成「最快」，直接把废节点顶到第一位 |
| 三档排序：实测通过 → 没测过 → 实测不通 | 没测过的不等于坏了，不该垫底；确认不通的才垫底。档内保持上游原顺序，不做无谓抖动 |
| 任何异常都退回原文顺序 | 订阅是整个服务的入口。为了排个序把订阅搞挂，代价远大于收益 |
| 复用 `latency_budget_ms` 预算 | 超了就按已测到的排，绝不把请求拖过 Workers 的墙钟 |

**验收**：`tools/check-latency.mjs` 从 26 项扩到 45 项。新增的 19 项里最关键的三条：
① 顺序真的是按延迟升序（原顺序 A→B→C，实测后 B→C→A）；② TTL 内**一次探测都不发**、
过期才重测；③ 不通的记 `null` 而不是 `0`。
按 AGENTS 第 5 节做了牙齿验证：去掉 `.sort()` → 5 条变红；忽略 TTL → 1 条变红；
不通的记成 `0` → 2 条变红。

**还没做的（有意留着）**：带 TTL 的延迟缓存已经就位，下面两个落点可以直接复用它，
但这次不一起上 —— 它们各自有独立的失败模式，混在一起出问题时分不清是谁的锅：

- **代理上游「换路」替代「补发」**：现在 hedge 是同一个域名补发第二遍，慢的是那个 IP 时
  补发只是再慢一次。改成首请求走域名、超时后补发到实测最快的 IP（URL 用 IP、
  `Host` 头保持原域名）。收益最大，但有 TLS/SNI 的坑，建议先在单个站点上开开关试。
- **节点健康检查按延迟淘汰**：`pool_good_ips` 现在是二值判定（通就行），可以加一条
  「连续 N 次实测超阈值自动降权 / 剔除」。

## 迭代 13：部署压缩（开 → 炸两次 → 回滚）

**来源**：部署产物 867 KB，距 Cloudflare 免费版 1 MiB 上限越来越近，想先压出余量。

**方案**：`wrangler.toml` 加 `minify = true`，867 KB → 535 KB（-38%）；同时把注入浏览器的脚本
从「靠全局名传数据」改成**实参传数据**，并新增 `tools/check-minify.mjs` 钉住这个写法。

**结果**：开了之后连着两次线上事故，两次都**不在 Worker 日志里**（详见
[07-踩坑记录](./07-踩坑记录.md) 第 19 条）：

| 次 | 现象 | 病根 |
|---|---|---|
| 1 | 「CF 用量」「访问统计」卡在加载态，按钮全失灵 | 注入脚本前半段是字符串字面量、后半段引用模块级标识符，压缩后名字对不上 |
| 2 | 整站 `ReferenceError: o is not defined` | 70 KB 外壳脚本里**引用了模块级标识符的函数**被改名成单字母 |

第二次还暴露了一个定位陷阱：`kp` / `o` 是 **wrangler 自带 esbuild** 分配的名字，
本地用 esbuild 压出来的名字跟它不一样 —— 所以本地怎么压都复现不出来。

**决定：回滚，不再启用**。867 KB 距 1 MiB 还有余量，体积不是当前瓶颈；为省 38% 换一次
线上全站不可用，这笔账不划算。回滚内容：`wrangler.toml` 删掉 `minify` 并写明不要再开、
删 `tools/check-minify.mjs` 与 CI 步骤、断言合计 783 → 776（21 → 20 套）。

**保留**：实参传数据这条纪律 —— 它本身更健壮，跟开不开压缩无关。

**教训**：**产物形态变了，源码层面的自洽就不作数了。** 凡是把源码当字符串送出去的地方
（`toString()` 注入、模板拼接、代码生成），都要假设标识符会被改名；只能依赖**同一份产出的
内部结构**，不能依赖名字本身。另外——本地自检跑的是源码，**压不压缩是两种产物**，
用源码的绿去担保产物的绿，本身就是个假判据。

## 迭代 14：浏览器测速结果要真的被采用

**来源**：一句追问 ——「浏览器自动优选有用吗，以现在的逻辑」。

**查出来的事实**：它只兑现了一半。而且顺带发现，迭代 12 的订阅排序也只兑现了一半，
两者是**同一个病根**：排序用的延迟数字，不是从用户网络量出来的。

### 病根：测量起点决定排序，而服务端只能在 CF 自己的网络里测

同一批 24 个 IP（服务端已排好序的订阅里取前 12 + 后 12），换两个网络各测 3 次取中位：

| 测量起点 | 前 12 中位 | 后 12 中位 | 差距 |
|---|---|---|---|
| 沙箱直连 | 687 ms | 814 ms | 127 ms（有区分度） |
| 经用户节点（美国出口） | 727 ms | 738 ms | 11 ms（等于没排） |

两组排序的**斯皮尔曼相关系数 rho = −0.056**（近似零相关）。也就是说：服务端排出来的
「最快」，换一个网络看基本是随机顺序。CF 内部看 CF 的边缘 IP，大家都近、都快、都差不多。

（附带发现：`http://<IP>/__api/config` 的耗时里还混着 Worker 冷启动 —— 同一 IP 裸 https
握手失败只要 0.10 s，走 http 探活却要 0.56 s。服务端这个数字连「纯网络延迟」都算不上。）

### 断点在哪：浏览器测出来的顺序，半路被扔了

浏览器自动优选（`admin.js` 的 `measureIp`）是全局唯一能从**用户网络**出发测量的入口。
但改之前它测完只做一件事：把前 15 个 IP 填进优选池输入框，**延迟数字当场丢掉**。
之后 `dns.js` 的自动优选走二值判定（`latency_enabled` 默认 false），顺序变成
「谁先探到谁在前」，最后只写 `max_targets`（默认 2）条 A 记录 —— 跟用户测的快慢无关。

所以它在改之前实际是个「**筛 15 个候选**」的工具，不是「优选」。

### 改动：把分工讲清楚 —— 浏览器定「谁快」，服务端定「谁通」

新增 `src/pickspeed.js`：存 `{ip: 毫秒}` 表（KV `PICK_SPEED`，带时间戳），自动优选在
**通断过滤之后**用它重排一次；测过的按毫秒升序在前，没测过的垫后并保持原顺序。

| 环节 | 以前 | 现在 |
|---|---|---|
| 浏览器测速结果 | 只留 IP 名单，数字丢弃 | 连毫秒一起存（`/__api/pick-speed`） |
| 测完要不要手动保存 | 要手动点「保存」 | 自动落库，并回显保存结果 |
| 服务端自动优选 | 二值判定，顺序 = 谁先探到谁在前 | 只剔掉不通的，顺序用浏览器那张表 |
| 结果可信度 | 无提示 | 区分度自检：全部挤在一起就明说「可能是在代理状态下测的」 |

**取舍**：

| 决定 | 为什么 |
|---|---|
| 只重排**已探通**的 IP | 用户侧再快，服务端判不通的也不能上位 —— 通断是服务端的活 |
| 未测过的垫后、保持原相对顺序 | 未知 ≠ 慢；乱动会把「没测过」错判成「最差」 |
| 整表共用一个时间戳 | 换网络后旧数据一起过期，不会出现「一半新的混着一半旧的」 |
| 不生效时如实回报 `reason`（`disabled`/`empty`/`stale`/`no-match`） | 「没排」和「排了但顺序没变」是两件事，混在一起就再也查不清 |
| 延迟表算运行数据，不进运行参数注册表 | 与 `HC_LAST_RUN` 同类；可配的部分（开关、有效期）才进 SPEC |

新增运行参数两个（面板「配置中心 → 优选与候选」）：`pick_speed_enabled`（默认开）、
`pick_speed_ttl_ms`（默认 12 小时）。

**已知边界**（不装作已经解决）：开着代理访问面板时，浏览器测到的是「出口节点 → CF」，
不是「你 → CF」—— 此时数值会全挤在一起，代码只能**识破并提示**，没法根治（浏览器拿不到
「如果不走代理会多快」）。1034 仍靠写完 A 记录后的域名自检回滚。

**验收**：`check-latency` 45 → **66** 项（新增 [12] 表存取与排序 / [13] 区分度自检 /
[14] 接口链路 / [15] 手动应用同口径），合计断言 795 → 818。牙齿验证三处各改坏一次，
判据都如实变红：去掉 `.sort()` → 红 2 条；忽略有效期 → 红 1 条；不看开关 → 红 1 条。

## 迭代 15：健康检查也有了「快慢」这一维 + 新手部署文档

**来源**：上一轮留的两个落点之一「节点健康检查按延迟淘汰」，加上一条反馈 —— 部署文档
对第一次用的人不友好。

### 慢节点淘汰：用哪把尺子，是这次唯一重要的问题

健康检查（`.github/workflows/healthcheck.yml`）以前只判通不通：一个 800ms 才响应的节点，
只要返回 200，就能一直占着 A 记录。这次给它加上快慢这一维。

**但判据绝不能用服务端探测的数字** —— 迭代 14 已经实测过，服务端视角的排序与用户视角
近似零相关（rho = −0.056）。用 GitHub Actions runner 的延迟去淘汰，等于用一把与用户无关的
尺子挑节点，会把「对你最快」的那个误杀掉。

所以判据只用**浏览器测速表**（`PICK_SPEED`）—— 那是唯一从用户网络量出来的数字：

| 规则 | 为什么 |
|---|---|
| 阈值 = max(最快 × 倍数, 绝对下限) | 只看倍数会出事：最快 30ms / 最慢 90ms 也是"三倍"，其实谁都一样快 |
| 少于 3 个样本不判 | 样本太少时"最慢"很可能只是没测准 |
| 至少保留 N 个 | 把池子掏空比留着慢的糟得多 —— 淘汰之后没得选，优选只能去订阅里现拉 |
| 过期 / 开关关闭 → **清空**名单 | 换网络后旧数字已不能作数，留着就是用失效的尺子继续淘汰 |

落到两处：**自动优选**剔除慢节点（候选不够时不剔）、**健康检查**候选过滤 + 扫描结果
按用户侧延迟排序取前 6（原来是 `sort -u`，字典序 = 随机挑，自愈很可能换到"通但很慢"的节点）。

新增 `pickSlow` / `withoutSlow` 两个纯函数（判据只此一份）、`/__api/pool-slow`、
运行参数 4 个（`hc_slow_evict` 默认开、`hc_slow_factor` 3 倍、`hc_slow_floor_ms` 600ms、
`hc_keep_min` 2 个）。

**验收**：`check-latency` 66 → **85** 项，合计 818 → 837。牙齿验证三处：去掉绝对下限 → 红 1 条；
去掉保留下限 → 红 1 条；过期不清空 → 红 1 条。

### 部署文档：先讲「不改这个 ID 就一定失败」

新增 [docs/11-新手部署手把手.md](../docs/11-新手部署手把手.md)（README 与 00-总览都挂了入口）。
写的时候核对了一遍真实流程，发现对新手最致命的一点：**`wrangler.toml` 里的
`database_id` / KV `id` 是本项目账号下的资源门牌号**，fork 后不改会直接部署失败 ——
这一条原来散落在 README 的资源表里，不显眼，现在单独作为「第 3 步」并标了「最容易漏」。

其余按"每步有预期结果"组织：4 个要从 Cloudflare 拿的值 → 填 ID → 填 Secrets → 点一下
Actions → 进面板 → 必做三件事（含"测速别开代理"）→ 三条 curl 验收 → 常见问题对照表。

## 迭代 10：配置页重构 + 系统操作手册

**来源**：两条反馈合起来指向同一个问题。

1. 「配置选项卡里面的内容有点乱，希望更简洁直观」；
2. 「优选池 & 健康检查的内容在好几个选项卡里都有，改为只有一个选项卡里有」。

**先查根因，再动手**。第 2 条的成因不是设计问题，而是一个漏写的属性：

```html
<div class="card" id="poolCard">            <!-- 漏了 data-pane -->
```

面板的分区切换是按 `data-pane` 决定显隐的，没有这个属性的卡片不参与切换 —— 于是「优选池 &
健康检查」在**每一个**选项卡下都常驻显示。一行属性，表现成"到处都有"。

第 1 条的成因则是结构问题：每个功能都有自己的选项卡，而「配置」页又把所有功能的表单
原样抄了一遍。11 个分组、30 个接口块全部摊开，自然又长又乱，更糟的是
**同一个配置出现了两份可编辑入口** —— 改完一边忘了另一边，就会出现
「面板显示 A、实际生效 B」这种极难排查的问题。

**方案**：把「配置」页重新定位为**设置中心 + 索引**。

- 目录里给分组加 `tab` 声明，表示「这块内容由哪个选项卡承载」。标了就不再在配置页渲染表单，
  只留一行跳转。这条规则统一适用于站点、优选 IP、伪装、主题、临时链接。
- 配置页只保留**没有独立选项卡**的设置：访问统计、限流防滥用、告警通知。
  外加诊断类工具（优选候选拉取、上游测速）和一张跳转索引。
- 顺手修好漏写的 `data-pane`，让优选池回到它该在的那一屏。

**界面上的具体改进**：

| 之前 | 之后 |
|---|---|
| 进页面必须点「读取当前值」才知道当前配置 | 进页面自动加载当前值 |
| 参数竖排一列，11 个字段的卡片高得离谱 | 两列自适应网格，长文本跨整行 |
| 基础项与调优项混在一起 | 调优项收进「进阶选项」折叠区，默认收起 |
| 查询与动作接口平铺在同一层 | 收进折叠的「工具」区，按钮文案区分「查看 / 执行 / 确认执行」 |
| 布尔值用「是 / 否」下拉 | 开关控件，一眼看出当前状态 |
| 字段说明塞在标签括号里 | 标签保持干净，说明放标签下方；数值带单位后缀 |
| 敏感项不知道配没配 | 标签旁显示「已配置」徽标，留空即不修改 |
| 改没改看不出来 | 有未保存改动时标色 + 保存按钮才可点，另有「还原」 |
| 前端脚本用字符串拼出来 | 写成真实函数再注入，可读、可跳转定义、能被语法检查 |

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 归属判定写在目录（`group.tab`）而不是界面代码里 | 加功能时只需在目录声明归属，界面自动跟随；写死在界面里迟早漏一处 |
| 字段类型与默认值从模块 SPEC 读，不在目录重抄 | 默认值只存在一份。目录重抄一遍就会分叉，而且分叉得很安静 |
| 配置页保留跳转行而不是彻底删干净 | 索引价值仍在：一眼能看到系统有哪些功能、各自在哪一屏 |
| 手册正文手写，速查表由脚本生成 | 写法与取舍要人写；字段名、默认值、环境变量是事实，手抄必然过期 |
| 自检里加「同一份配置全页只出现一次」 | 这条正是本次问题的断言化 —— 下次谁再复制一份表单，CI 会直接拦下 |

**验收**：

- 新增 `tools/check-configui.mjs`（99 项）：目录与 SPEC 字段双向核对、每项恰好渲染一次、
  隐藏项不出现、**全页没有重复的设置表单**、卡片归属的选项卡都存在、危险动作有二次确认、
  目录内容进 HTML 全部转义、目录里的接口在 `admin.js` 里都真的有分支。
- 同一脚本里还钉住**各选项卡的内容宽度**：卡片内边距、字段最小列宽、栅格间距只能来自
  主题变量，并按真实页面宽度算出两边的字段宽必须相等。
  （起因：「临时链接」和「配置」两页的输入框比前面几个选项卡窄一圈。）
- 新增 `tools/gen-manual.mjs`：手册附录由目录生成，`--check` 模式进 CI，文档与代码不同步就红。
- 新增 `docs/09-系统操作手册.md`：面向使用者的操作手册，含症状对照表与速查表。

## 迭代 9：防护与分享（限流 / 告警 / 临时链接）

**来源**：一次给出四个方向（访问统计、限流防滥用、告警通知、站点临时访问链接）。
统计先落地，本轮把剩下三个一起做完，并补上「登录页也要跟着主题走」这半步。

**方案**：三个模块共用同一套配置层与同一份接口清单 —— 加一条配置，面板表单自动出现，
不需要动 UI 代码。三者的**关键项一律默认关闭**，升级不改变既有部署行为。

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 限流桶状态放内存、跨 isolate 不强求精确 | 限流是防滥用不是计费。为「绝对精确」引入存储写入，会把每个正常请求都变慢 |
| 面板口与代理口分开限速 | 合在一起会出现「有人刷面板 → 反代业务一起被限死」的连带故障 |
| 告警 Webhook 地址不下发明文 | 它本身就是一条「发什么都能进你群」的凭据，面板只回显「是否已配置」 |
| 告警带冷却窗口 | 上游抖动时同一事件会连着触发几十次，不复用冷却等于把群刷爆 |
| 临时链接的计数与到期都在服务端判定 | 写进链接里就会被伪造；`有效期` 与 `最大次数` **任一先到即失效** |
| 登录页接入主题系统、但伪装入口保持中性 | 登录页是管理员自己看的，该跟主题；伪装入口是给陌生人看的，套上任何特征都是指纹 |

**验收**：`tools/check-guard.mjs` 51 项，含「默认关闭不误伤」「封禁 / 一键解封」「已登录豁免」
「告警记录递归脱敏」「临时链接超额与到期双重失效」；线上 `check-live.mjs` 同步加了这三段。

## 迭代 8：外观主题（10 套 + 自定义 + 自动轮换）

**来源**：「面板切换主题应该是不一样的，最好像换了一个系统一样」，而且要有自定义主题；
后来补了一条：**主题可以自动轮换**，避免长期不换审美疲劳。

**方案**：主题就是数据 —— 每套主题只是一张「CSS 变量 → 取值」的表，页面样式由表生成，
加第 11 套 = 往表里加一条。差异不只配色，还同时定义字体、圆角、阴影，
需要时再补一小段**带作用域**的结构样式（改标签栏 / 按钮形状），所以切换是"整体换肤"。

**关键取舍**：

| 取舍 | 为什么 |
|---|---|
| 主题表放在 `src/themes.js`，不在页面里写分支 | 加主题不改页面代码；页面里散落 `data-theme` 分支等于每加一套改十处 |
| 自定义主题的值做严格过滤（禁 `{} ; @ < > \` 引号） | 它会被拼进 `<style>` 和元素的 `style` 属性，一个 `}` 或引号就能打穿整页样式 |
| 补充样式强制加 `[data-theme="x"]` 前缀 | 不加就会在所有主题下生效、互相覆盖；这条同时是"换主题像换系统"的前提 |
| 轮换用**绝对时间切片**（`epoch 分钟 / 间隔` 取模） | 全球 isolate 各自算出同一套；用进程内自增会变成"同一个人刷新两次换两套" |
| 访客选择存 `localStorage`，全站默认才写服务端 | 个人偏好不该影响别人；要全员生效必须显式点「设为全站默认」 |

**验收**：`tools/check-themes.mjs` 33 项，含「10 套都在」「自定义能存能删」「CSS 注入被拒」
「轮换结果全球一致 / 池子配错退回全部」。

## 迭代 7：删除 README 示例反代链接

**来源**：README 里的示例链接指向真实可用的反代路径。

**判断**：示例链接一旦指向真实站点，就等于帮别人做目录。直接删掉，同时给 `PROXY_HOST`
