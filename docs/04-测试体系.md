# 04 · 测试体系

## 设计原则：三层，越往上越贵越真实

```
单元测试        各自模块的规则正确性，纯逻辑，秒级
    ↑
路由级冒烟      从 handleRequest 进入，守住调用链断层
    ↑
端到端实测      真实网络 + 真实浏览器 + 真实节点
```

**为什么要中间那层** —— 因为它是被一次真实事故催出来的：

`proxyRequest` 增加了 `env` 参数、`dispatchProxy` 没跟着传，结果是**每个代理页面都 502**。
而当时 `rewrite` / `compress` / `disguise` 的单测**全绿**，因为它们都没走完整链路。
单元测试各自通过、组合起来却炸，这类问题只有把整条路跑通才抓得住。

合计 **1147 项**断言，分布在 **22 套纯离线脚本**里；另有 `check-live`（需线上地址与口令）
与 `check-e2e`（真实浏览器）两套走线上，不计入。

这个数字**不再由人手工累加** —— `node tools/count-asserts.mjs` 跑一遍即出全部分项与总数。
之所以要这样：上一版写的是 1074，实际对着脚本一项项数出来是 1082，中间还连着三个
更小的抄写偏差（guard 记 52 / 实 51、themes 记 44 / 实 42、smoke 停在 50 没跟上新增的 11 项）。
数字由人手抄一遍，一定会抄错，而且错得毫无声响 —— 从这一版起，表格右边的那一列只认脚本输出。

上表每一套都已挂进 `.github/workflows/verify.yml`
的 unit job —— 这一条看似理所当然，实际曾漏过三套共 98 项（详见 [07-踩坑记录](./07-踩坑记录.md) 第 23 条），
教训是：**检查挂不进 CI，就等于没写检查**。

`check-settings.mjs` 是这次配置统一化新增的。它防的是**「这个参数只有环境变量能改」**——
面板上根本没有入口，用户以为改不到、只能重新部署。脚本端到端真跑一遍：把渲染产物里的
表单脚本抠出来沙箱执行、提交保存、再用运行时入口重新读一遍，断言新值立刻生效；
同时确认密钥类字段只回显「是否已配置」、值不出现在任何返回体里。
历史状态：`SUB_STRICT / SUB_CANDIDATE_LIMIT / DNS_BUDGET_MS / PROXY_HEDGE_MS /
CF_API_TOKEN / CF_ZONE_ID / GEOIP_BATCH_SIZE / GH_ACTIONS_URL` 等 20+ 项此前都属于这一类。

它还有一条「写路径」纪律：**字段名只有 `SETTINGS_SPEC` 一套，不认识的键当场报 400**。
以前是静默忽略 —— 字段名写错一个字母、或某个调用方还在用旧别名时，接口照样返回
200「已保存」，而一个字节都没写进去。表现就是「点了保存、提示成功、值没变」，
不报错、不抛异常、日志也干净。同一件事在 `check-nodetag.mjs` 第 8 段也钉了一遍
（用旧别名 `{enabled, style}` 调 `/__api/node-tag` 必须被拒）。

`check-configui.mjs` 值得单独说一句：它防的不是崩溃，而是**静默地对不上**。
模块的 SPEC 加了字段而目录忘了加，界面就少一个输入框 —— 用户永远改不到那个配置，
却不会看到任何报错。它还守着一条结构纪律：**同一份配置全页只能出现一次**。
正是这条纪律的缺失，让优选池曾经同时长在两个选项卡里。

它也会**反向**核对一次：`admin.js` 里新加了接口而目录没跟上，是同一类事故的另一种长相 ——
功能能调，但面板上不渲染、手册里也不收录，而且什么都不会报错。这条检查带一张白名单，
只放「刻意不进目录」的接口（内部探活 `GET /__api/config`、伪装页预览 `/__api/disguise-preview`），
每条都要写明理由；白名单本身也被检查（写了却不生效同样会红）。

它还管**宽度**。页面里任何一处横向度量（卡片内边距、字段最小列宽、栅格间距、
页面留白）都只能来自主题变量，而且会按真实页面宽度算一遍：配置页的自动列数
必须和站点页的固定列数一致，算出来的字段宽必须相等。样式分叉不会报错，
只会让人看着别扭 —— 所以这类问题得靠数值断言，不能靠肉眼回归。
（这条是补的：曾经「临时链接」和「配置」两页的输入框比其它选项卡窄一圈，
三个度量各写了一份。）

### `tooth-storage.mjs`：给检查本身装牙齿

`check-*.mjs` 跑一遍全绿，这件事**本身没有任何信息量** —— 谁都能写出一段永远为真的断言。
真正有信息的只有一句：「把实现还原成旧写法，它红不红」。AGENTS 第 5 节把它立成了纪律，
但这个纪律此前全靠自觉：做一遍、截图、写进文档，然后随着下一次改动慢慢失去意义。

`tools/tooth-storage.mjs` 把这件事固化成一条命令：它把 `src/memstore.js` 逐个改成 14 种
「退化写法」（降级后仍打后端、探测成功就自动切回、写回无脑覆盖冲突、写失败吞掉异常、
每次绑定都新建状态、种子不灌、影子副本不搬、阈值不同步、自动降级谎报全站、墓碑漏进列表、
不记待写回、手动切内存不预加载……），每改一次就跑一遍 `check-storage.mjs`，要求它必须红。

判定口径刻意比「有没有崩」更严：**崩溃不算通过**。崩溃确实会让 CI 变红，但打印出来的是
一屏调用栈而不是「哪一项坏了」—— 夜里排障时这等于没有提示。所以这里要求「退出码非 0
**且**打印出失败项」。立这条口径是因为真吃过亏：最初三个变异（降级后仍读后端、每次绑定都
新建状态、阈值不同步）在对照脚本里都显示成「绿的」，实际上是脚本崩了 —— 对照脚本把崩溃
当成了「没有失败项」（教训同样收在 [07-踩坑记录](./07-踩坑记录.md) 第 26 条）。对应的修法
有两处：断言里的裸读换成会吞异常的助手，让坏实现得到的是一个可读的哨兵值而不是一屏堆栈；
判定口径也收紧成「不仅要红，还要红得看得懂」。

变异脚本会改动源文件，所以它对安全性有一条硬要求：`process.on('exit')` 与 `uncaughtException`
里都挂了还原钩子 —— 无论怎么退出（含 Ctrl-C 与断言抛错），都不许把改坏的实现留在磁盘上。

## 文档也是被检查的对象

`tools/gen-manual.mjs` 从接口目录与各模块 SPEC 生成操作手册的速查表附录。
字段名、默认值、环境变量名这类"事实"手抄必然过期，所以要生成：

```bash
node tools/gen-manual.mjs          # 检查手册与代码是否同步（CI 跑这个）
node tools/gen-manual.mjs --write  # 重新生成附录
```

CI 里跑的是检查模式，目录改过而手册没重新生成会直接失败。

## `check-nodes.py`：四级递进，只有 L4 才算证据

这是本项目唯一做**真实联网穿透**的测试，也是最容易得出错误结论的一个。

| 级别 | 验证了什么 | 到这一级能说明什么 |
|---|---|---|
| `L1` | TCP 端口可达 | 至少没被墙、没关机 |
| `L2` | 带 SNI 完成 TLS 握手 | 证书与 SNI 配置没坏 |
| `L3` | WebSocket 拿到 101 | 反代入口是通的 |
| **`L4`** | **真发一条 VLESS 请求把数据代理出网** | **端到端可用** |

**停在 L3 不等于能用**。历史上出现过「79 个节点全部卡在 L3」的报告，看起来像节点全坏，
实际全部健康 —— 是判断逻辑自己的 bug（详见 [07-踩坑记录](./07-踩坑记录.md) 第 4、5 条）。

最新实测（81 个节点）：

```
L4: 79    L2: 1    L1: 1
不可直接使用（TCP/TLS 就不通）: 2
```

### 两个必须避开的坑（脚本里已处理）

1. **探测目标要避开 Cloudflare 托管的站点**。CF 对自己边缘 IP 发来的明文 HTTP 请求直接回 400，
   用它当判据会把健康节点误判成坏的。脚本用的是 `httpbin.org` / `www.baidu.com` / `www.qq.com`。
2. **每个目标必须新开一条连接**。同一条 WS 连接上重试第二个目标时，服务端已经把它当作
   上一个流在收 —— 第一个失败会连累后面全部失败。

## 本地起一套验证环境

```bash
# 起本地目标站 + 代理，浏览器直接点
node tools/dev-fixture.mjs 8799
SEED_SITES="demo=http://127.0.0.1:8799" node tools/local-dev.mjs 8787
# → http://127.0.0.1:8787/p/demo/
```

`dev-fixture.mjs` 的内容是刻意设计的陷阱集合：JS 里的 `//` 注释、`//# sourceMappingURL`、
CSS 的 `url()`、HTML 的 `<base>` / `srcset` / `integrity` —— 都是改写时容易被误伤的形态。

> **注意**：踩到第 9 条坑的情况 —— 测试前先确认 fixture 还活着（`curl 127.0.0.1:8799`），
> 否则代理会返回 502 `fetch failed`，很容易误判成代码问题。

## 怎么验证压缩真的生效

```bash
# 明文
curl -s http://127.0.0.1:8787/p/demo/ -H "Accept: text/html" -o /tmp/plain
# 压缩
curl -s http://127.0.0.1:8787/p/demo/ -H "Accept: text/html" \
     -H "Accept-Encoding: gzip" -o /tmp/gz
```

验收三条，缺一不可：

1. 响应带 `Content-Encoding: gzip` 和 `Vary: Accept-Encoding`
2. 体积显著变小（实测 45378 B → 7653 B，降到 17%）
3. **gzip 解压后与明文逐字节一致** ← 这条最关键，压缩搞坏内容的代价远大于不压缩
