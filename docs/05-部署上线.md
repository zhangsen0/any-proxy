# 05 · 部署上线

## 流水线三步

```
push → master
  ↓
① verify.yml            8 个自检脚本（unit job）+ 浏览器 e2e
  ↓  必须全绿
② deploy-cloudflare.yml Workers 部署（Secrets 注入 + backend 裁剪）
  ↓
③ healthcheck.yml       健康检查 + 自动修复
```

`deploy` 和 `healthcheck` 之间是 `workflow_run` 关系 —— 这个细节引发过一次事故，见下一节。

---

## 为什么不要绕过 CI 直接 `wrangler deploy`

本地也可以用 CF API Token 直接部署，**但不建议**：

GitHub Actions 在部署时会注入一批 Secrets 和变量：

```
PASSWORD            UUID
CLOUDFLARE_API_TOKEN
DISGUISE_PATH       DISGUISE_TOKEN         ← 伪装的进门凭据
STORAGE_BACKEND                             ← 决定 wrangler.toml 保留哪个 binding
PROXY_HOST                                  ← 健康检查的目标域名
WORKER_NAME  D1_DATABASE_ID  KV_NAMESPACE_ID  R2_BUCKET_NAME   ← 可选，指定已有资源才填
```

另外 `wrangler.toml` 里的资源 ID 是**占位符**（`__D1_DATABASE_ID__` 之类），
必须先由 `.github/scripts/prepare-deploy.py` 渲染成真实值 —— 它同时负责建资源、
按后端裁剪绑定。本地要跑 `wrangler dev` 就先执行 `python3 .github/scripts/prepare-deploy.py --local`
（用占位 ID、不碰云端）。

直接用 wrangler 部署会用本地 `wrangler.toml` 的配置，**这些注入项一个都没有** ——
结果是伪装进门凭据丢失（等于把自己锁在门外）、存储后端绑定错、占位符没被替换。

**规则**：要走 CI。除非明确知道自己在做什么，并且能接受重新配一遍所有 Secrets。

## 上线后怎么验收

按顺序跑，前三条不过就别往下走。

### 1. 伪装是否收敛（最高优先级）

```bash
curl -s https://<你的域名>/ | grep -o "<title>[^<]*</title>"
# 期望：伪装模板的标题，比如「站点维护中」

# 页面内不该出现任何面板痕迹
curl -s https://<你的域名>/ | grep -c "__admin\|__api\|Any-Proxy"
# 期望：0

# 敏感路径一律 404，而不是 302
for p in /__admin /__api/sites /admin; do
  curl -s -o /dev/null -w "$p -> %{http_code}\n" https://<你的域名>$p
done
```

> 特别检查有没有 **302**。返回 302 到登录页会把 `/__admin` 这类命名空间写进
> `Location` 头，伪装就白做了。

### 2. 两种进门方式

```bash
curl -s -o /dev/null -D - https://<你的域名>/site-status | grep -i "location\|set-cookie"
# 期望：302 + Set-Cookie: visited=1

curl -s -o /dev/null -D - "https://<你的域名>/?k=<你的口令>" | grep -i "set-cookie"
# 期望：同样下发 visited
```

带 cookie 再访问根路径应当能看到管理面板。

### 3. 反代与压缩

```bash
curl -s -D - -o /dev/null https://<你的域名>/p/<站点id>/ \
  -H "Accept: text/html" -H "Accept-Encoding: gzip" | grep -i "content-encoding"
# 期望：gzip
```

### 4. 订阅链路与国家标注

```bash
SUB_URL=https://<你的域名>/tsub/<id>
curl -s "$SUB_URL" -o /tmp/sub.txt
python3 tools/check-nodes.py /tmp/sub.txt
# 期望：绝大多数节点达到 L4
```

## 配额打满时的应急部署（内存模式）

D1 / KV 的额度用尽（或暂时不可用）时，常规部署会卡在 `wrangler d1 migrations apply`，
站点也可能整个打不开。这时候不必等额度恢复 —— 走**内存模式**：

**原理**：Worker 启动时把 `SEED_JSON` 的内容灌进进程内内存，之后所有读写都在内存里，
一个存储绑定都不要。环境变量**不占 D1 / KV 的读写额度**，所以它绕得开配额。

**代价必须说清**：

| 代价 | 说明 |
|---|---|
| 不持久 | 边缘实例重启 / 冷启动就回到种子那份内容，**这期间的改动会丢** |
| 需要手动切回 | 配额恢复后要点「写回」把改动搬进存储，再点「切回存储模式」 |
| 各实例之间不同步 | 内存里的东西只属于那一个实例 —— 面板顶部会如实标出「仅当前实例」 |

### 操作步骤

1. **把数据导出来**（需要一枚有 D1 读权限的 CF API 令牌）：

   ```bash
   node tools/export-seed.mjs --from-d1 --token <API令牌> --account <账户ID> --db <数据库ID> \
     --chunk 4096
   ```

   拿不到令牌也可以用 `wrangler d1 export any-proxy-db --remote --output dump.sql`，
   再 `node tools/export-seed.mjs --from-sql dump.sql --chunk 4096`。

2. **填到仓库变量**：脚本会按 `SEED_JSON`、`SEED_JSON_01`、`SEED_JSON_02` ……
   依次打印每一段该填进哪个变量。到 *Settings → Secrets and variables → Actions → Variables*
   逐个添加。**一个都不能漏** —— 漏一段的结果是站点能起来、返回也是 200，但数据是残缺的；
   部署脚本检测到编号不连续会当场报错，这正是为了拦它。

3. **切到内存模式**：同一个 Variables 页面里加 `STORAGE_BACKEND = memory`。

4. **push 触发部署**。此时 `prepare-deploy.py` 会摘掉 D1 / KV 两段绑定，也不跑迁移。

5. **验收**：打开管理面板，顶部应当有一条醒目的状态条写着「内存模式」，
   并列出「还有几个键没写回」。`/__api/storage` 返回的 `mode` 应为 `memory`。

### 配额恢复之后

在面板那条状态条上依次点 **探测** → **写回** → **切回存储模式**，
最后把 `STORAGE_BACKEND` 变量删掉（或改回 `d1`）再部署一次即可。

> ⚠️ **写回之前不要先删掉种子变量**：写回是把内存里的改动搬进存储，
> 这一步失败的话，干净的种子还在，重来一次就行。

### 单变量 5 KB 这件事

单个环境变量上限 **5 KB**（付费计划同样是 5 KB），一个 Worker 最多带 64 个（Free）。
所以上面的 `--chunk 4096` 是刻意的：留一点余量给多字节字符。超过 24 段（约 120 KB）
时请先用 `--only site:,APP_CONFIG` 只导必要的键 —— 统计类流水（`stats:`）默认就跳过，
它们丢了不心疼，重建一次就有。

## 回滚

Workers 没有「一键回滚到上个版本」的按钮，所以：

- 出问题优先**用新代码修**（小改动跟着 CI 走，几分钟）
- 实在要退回，回到目标 commit 重新走一遍 push → verify → deploy

这也是为什么每次改动要保持小粒度、commit message 要写清楚为什么（见
[03-开发规范](./03-开发规范.md) 第 8 条）—— 回滚时你需要在几分钟内定位到该回哪个 commit。
