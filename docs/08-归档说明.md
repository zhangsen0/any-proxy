# 08 · 归档说明

## 为什么归档

这个项目已经完成了它的周期：需求全部交付、测试全绿、部署上线并验收通过。
归档（archive）意味着**停止活跃维护**，而不是删除 —— 代码、文档、提交历史全部保留，
只是不再接受新的 issue 和 PR。

归档前最后一次完整验收的结果，见下方。

### 本轮踩到的两个环境坑（与项目代码无关，但很费时间）

1. **`git push` 报成功，远端分支却没变**。这台机器的 git 连 `refs/remotes/*` 都写不进，
   `origin/master` 会一直停在旧值（`git branch -v` 甚至显示「ahead N commits」），
   但 `FETCH_HEAD` 是正确的。判断远端真实状态要直接问 GitHub API 或 `git ls-remote`，
   别信本地引用。
2. **PR 显示冲突（dirty），内容其实不冲突**。当源分支与目标分支没有共同历史
   （例如提交成了孤立根提交）时，GitHub 无法计算合并基点，一律报冲突。
   这种情况不要去解冲突 —— 直接基于目标分支尖端重建分支、套上同一份文件树，最省事。

### 本轮踩到的两个环境坑（与项目代码无关，但很费时间）

1. **本机代理放行了 `api.github.com` 与 `codeload.github.com`，却连不上 `github.com`**。
   而 git 的 smart HTTP 恰好走 `github.com`，于是 `git push` 一路报
   `OpenSSL SSL_read: … unexpected eof while reading`（重试、改 HTTP/1.1、加大 postBuffer 都无效）。
   绕法：改用 GitHub 的 Git Data API（建 blob → 建 tree → 建 commit → 更新 ref）。
   `ref` 更新同样会触发 push 事件上的 CI；而且比对远端与本地提交 SHA 是否相同，
   能反过来证明内容没被改写 —— 这次两端都是 `34ad17cf`。
2. **Windows 的 `core.autocrlf` 会把工作区换成 CRLF**，`gen-manual.mjs --check` 逐行比对因此
   误报「手册与代码不一致」。修法：`git config core.autocrlf false && git config core.eol lf`。

### 本轮踩到的环境坑（与项目代码无关，但很费时间）

1. **PAT 失效 + GitHub MCP 未加载**。推送用的 PAT 直接返回 `401 Bad credentials`；
   GitHub MCP 在会话里是 `disabled: true`，工具列表里根本没有它。两条路同时堵死时，
   先确认哪条还能用，别在同一条上重试十次。
2. **Python 的「直连」其实也走代理**。`urllib` 不传 `ProxyHandler` 时会读 Windows 注册表里的
   系统代理 —— 于是「代理挂了就改直连」是假动作，两条路径报的是同一个错。
   禁代理必须显式写 `ProxyHandler({})`。
3. **本地 esbuild 压出来的名字 ≠ wrangler 压出来的名字**。`ReferenceError: o is not defined`
   里的 `o` 是 wrangler 自带 esbuild 分配的，本地怎么压都复现不出来。要验产物，
   就得拿**真正会部署的那一份产物**去验。
4. **云沙箱里 `github.com` 被网络策略拦掉时，不要拿 PAT 去喂公共镜像**。这类环境的表现是
   `github.com` 解析到一个假 IP（如 `198.18.0.14`）、TLS 握手被中断。这时搜到的各种
   「GitHub 加速镜像」能读不能信：拿一个空 token 去问 `api.github.com/user` 也会返回一个
   别人的账号 —— 说明它在替你带身份，你的 PAT 同样会被它看到。
   正解是**走自己的节点**：订阅里拿 vless 节点 → 本地起 Xray（SOCKS5）→
   `git -c http.proxy=socks5h://127.0.0.1:1080 push`，DNS 在远端解析，假 IP 也绕过去了。

### 这一轮**没做**的事（有意留着的）

延迟实测目前**只接了一处**（自动优选 DNS 更新时按快慢排序，且默认关闭）。
三个更有感的落点留给下一轮：订阅下发的节点按快慢排、代理上游「换路」替代「补发」、
节点健康检查按延迟淘汰 —— 它们都依赖同一份带 TTL 的延迟缓存，先做其中一个，
另外两个就能复用，不必三个一起上。

## 第五轮：订阅排序 + 浏览器测速真正参与优选（2026-09-18）

**触发**：一句追问 ——「浏览器自动优选有用吗，以现在的逻辑」。

**查出的事实**：两处延迟能力都只兑现了一半，而且是**同一个病根** —— 排序用的数字
不是从用户网络量出来的。关键证据是一次对照实验：同批 24 个 IP（服务端已排好序的订阅里
取前 12 + 后 12），换两个网络各测 3 次取中位 ——

| 测量起点 | 前 12 中位 | 后 12 中位 | 差距 |
|---|---|---|---|
| 沙箱直连 | 687 ms | 814 ms | 127 ms（有区分度） |
| 经用户节点（美国出口） | 727 ms | 738 ms | 11 ms（等于没排） |

两组排序的斯皮尔曼相关系数 **rho = −0.056**（近似零相关）。结论：服务端排出来的「最快」，
换一个网络看基本是随机顺序。另外还发现 `http://<IP>/__api/config` 的耗时里混着 Worker
冷启动（同一 IP 裸 https 握手失败只要 0.10 s，走 http 探活却要 0.56 s），连「纯网络延迟」
都算不上。

**两笔提交**：`709cff6` 把快慢排到订阅上（客户端通常拿第一个节点）；
`81a2737` 让浏览器测速结果真正参与自动优选 —— 浏览器定「谁快」，服务端只定「谁通」。

| 步骤 | 做了什么 |
|---|---|
| 1 | 仓库 Settings → Unarchive（第四轮补完 `e08ad90` 后一直没重新归档） |
| 2 | 对照实验确认「测量起点决定排序」，服务端视角对用户近似随机 |
| 3 | `709cff6`：新增 `src/sublat.js`（订阅出口重排 + KV TTL 缓存 + 三档稳定排序），`router.js` 的 `/sub` 接上 |
| 4 | 线上抽查（部署域名 + 真实 token）：两次拉取各 81 个节点，交集 36 个且**交集内相对顺序完全一致**；`/sub` 五次耗时 3.22 / 4.58 / 4.56 / 2.81 / 3.89 s（命中缓存那几次也 3~4.5 s → 时间主要花在上游拉取与国家标注，探测的边际成本约等于 0） |

### 第五轮的一条设计决定（值得单独记）

**不再让服务端排快慢。** 服务端只能回答「通不通」，快慢交给能从用户网络测量的那一侧：
订阅场景退而求其次用服务端数字（冷启动噪声 + 视角偏差都在，但至少把不通的垫了底），
自动优选场景改用浏览器实测值。两者都不假装「服务端测出来的快 = 用户感觉到的快」。

**已知边界**：开着代理访问面板时，浏览器测到的是「出口节点 → CF」而不是「你 → CF」，
此时数值会全挤在一起 —— 代码只能**识破并提示**（`spread()` 判极差与相对离散度），
没法根治，因为浏览器拿不到「如果不走代理会多快」。

如果要把这个系统交给别人，除了仓库本身，还需要单独传递（**不要写进仓库**）：

```
管理面板口令（PASSWORD）
节点 UUID
伪装隐蔽路径 /admin-url：DISGUISE_PATH 的值
伪装 URL 口令：DISGUISE_TOKEN 的值
```

以及建议：
- 重新签发一个最小作用域的 Cloudflare Token 并更新 Secrets
- 把 `docs/07-踩坑记录.md` 读一遍 —— 那里记录的价值比代码本身更难重建
