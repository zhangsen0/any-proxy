# 08 · 归档说明

## 为什么归档

这个项目已经完成了它的周期：需求全部交付、测试全绿、部署上线并验收通过。
归档（archive）意味着**停止活跃维护**，而不是删除 —— 代码、文档、提交历史全部保留，
只是不再接受新的 issue 和 PR。

归档前最后一次完整验收的结果，见下方。

### 本轮踩到的两个环境坑（与项目代码无关，但很费时间）

1. **`git push` 报成功，远端分支却没变**。这台机器的 git 连 `refs/remotes/*` 都写不进，
   `origin/master` 会一直停在旧值（`git branch -v` 甚至显示「ahead N commits」），
   但 `FETCH_HEAD` 是正确的。判断远端真实状态要直接问 GitHub API 或 `git ls-remote`，
   别信本地引用。
2. **PR 显示冲突（dirty），内容其实不冲突**。当源分支与目标分支没有共同历史
   （例如提交成了孤立根提交）时，GitHub 无法计算合并基点，一律报冲突。
   这种情况不要去解冲突 —— 直接基于目标分支尖端重建分支、套上同一份文件树，最省事。

## 第三轮：解除归档 → 配置统一化 → 再归档

**需求**：统一所有配置 —— 除了必须固定的部署形态项，其他所有配置都必须能在页面上配置，且改完立即生效。

**做法**：见 [01-需求与迭代](./01-需求与迭代.md) 的「迭代 11」。要点是把原先**只认环境变量**的
20+ 个运营参数（订阅严格模式、候选上限、探测并发与超时、优选总预算、转发对冲阈值、
CF API 凭据与端点、GeoIP 批量条数、面板运维入口、哈希盐值…）收进 `src/settings.js` 的
`SETTINGS_SPEC`：一处声明，运行时取值 / 面板表单 / 操作手册三处消费；保存后由
`notifyConfigChange` 广播清掉各模块的进程内快照，因此**下一次请求就按新值跑**，不用重新部署。

| 步骤 | 做了什么 |
|---|---|
| 1 | 本地改代码：新增 `src/settings.js` 与 `tools/check-settings.mjs`，改 12 个模块 + 目录 + 配置 UI |
| 2 | 跑全量离线自检（20 套）与 `gen-manual.mjs --check`，并按 AGENTS 第 5 节做牙齿验证 |
| 3 | 提交（中文提交信息）→ 更新远端 `master` → Actions 自动 Verify + Deploy |
| 4 | 线上核对：部署版本号 / CI 的 e2e 真浏览器校验 / 伪装收敛抽查 / 带口令的健康检查 |

### 本轮踩到的两个环境坑（与项目代码无关，但很费时间）

1. **本机代理放行了 `api.github.com` 与 `codeload.github.com`，却连不上 `github.com`**。
   而 git 的 smart HTTP 恰好走 `github.com`，于是 `git push` 一路报
   `OpenSSL SSL_read: … unexpected eof while reading`（重试、改 HTTP/1.1、加大 postBuffer 都无效）。
   绕法：改用 GitHub 的 Git Data API（建 blob → 建 tree → 建 commit → 更新 ref）。
   `ref` 更新同样会触发 push 事件上的 CI；而且比对远端与本地提交 SHA 是否相同，
   能反过来证明内容没被改写 —— 这次两端都是 `34ad17cf`。
2. **Windows 的 `core.autocrlf` 会把工作区换成 CRLF**，`gen-manual.mjs --check` 逐行比对因此
   误报「手册与代码不一致」。修法：`git config core.autocrlf false && git config core.eol lf`。

### 这一轮**没做**的事（有意留着的）

管理页里还剩两处**手写表单**没走注册表渲染：订阅链接卡片、节点国家标注卡片。
它们已经满足「面板可改 + 保存即生效」，且取值与校验都已指向唯一真源，
所以不属于「改不到」的问题；但表单结构仍是手写的，属于「通用化」的下一个候选。
`src/settings.js` 里已有 `ownTab` 标记（标明「本字段的编辑入口在别的选项卡」），
`schema` 侧也已支持 `select`/`textarea` 等控件，改造时不需要新机制。

## 归档后：还能做什么 / 不能做什么

| | 归档后 |
|---|---|
| 读代码、下载、fork | ✅ 可以 |
| 提 issue / PR | ❌ 不可以 |
| Cloudflare Worker 线上运行 | ✅ **照常运行**，归档 GitHub 仓库不影响已部署的服务 |
| 定时任务（cron） | ✅ 照常触发 |
| Secrets 轮换 | ⚠️ 需要时**先取消归档**再改 Settings |

**最重要的一条**：归档仓库**不会影响已经部署到 Cloudflare 的 Worker**。
cron、优选、健康检查、伪装全部照旧。只有当 Secrets 过期或要改配置时才需要解除归档。

## 如果要重新开始维护

1. 在仓库 Settings → 取消归档（Unarchive）
2. 检查 GitHub Secrets 是否过期（`PASSWORD` / `UUID` / `CLOUDFLARE_API_TOKEN` /
   `DISGUISE_PATH` / `DISGUISE_TOKEN` / `STORAGE_BACKEND` / `PROXY_HOST`）
3. 手动跑一次 `Health Check & Auto Repair` 确认自愈链路还通
4. 按 [05-部署上线](./05-部署上线.md) 的验收清单过一遍
